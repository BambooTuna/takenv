# UI Check Skill（見た目・利用シーン統合監査）

## Purpose

UI 実装やスクリーンショットを、以下の 3 軸で監査する。

1. **見た目・実装品質**: デザインシステム primitive 逸脱 / 独自実装の混入、LLM が作りがちな見た目先行 UI、視覚表現・状態表現の一貫性
2. **利用シーン・動線**: 利用者の業務シーン・利用頻度・主副動線、情報優先度・引き算（S/N）、次アクション・状態・復旧
3. **出力面・宛先**: エクスポート資料（xlsx / PDF）・通知など画面以外の出力面の項目・文言。宛先分離（社内情報の漏出 / 内部語の露出 / 読み手の語彙）と、表・文書に固有の引き算（情報量ゼロの列 / 数字の一人歩き）

このスキルは **検出専用**。新規画面の構図づくりは [ui-design](../ui-design/SKILL.md)、実装後の総合レビューは [ui-review](../ui-review/SKILL.md) を使う。監査対象は画面に限らず、ユーザー・顧客の目に触れる成果物（エクスポート・帳票・通知文面）を含む。

## You Must Read

- [references/checklist.md](./references/checklist.md) — 監査チェックリスト。必ず読む。
- [../ui-design/patterns.md](../ui-design/patterns.md) — 情報設計原則（ゼロベース・出自タグ / priority hierarchy・段階開示 / S/N / 動線重複の排除 / 宛先分離）の正本。checklist はこの原則の症状カタログであり、解釈が割れたらこちらを正とする。
- 対象の UI コンポーネント本体と、それが使う共通 UI primitive（例: `<frontend-src>/components/ui/*.tsx` 等、プロジェクトのデザインシステム実体）。
- 変更差分がある場合は `git diff`。スクリーンショットがある場合は画像も見る。

## 基本姿勢

- **既存 UI を出発点にしない。** まず利用シーンと目的関数を言語化する。既存実装は制約ではなく仮説。
- **全要素に存在意義の説明責任を課す。** 「誰が・どんな状況で・なぜそれを見るのか・何に使うのか」を全要素について説明できることが合格ライン。説明できない/説明が非合理的な要素は悪い要素。判断には確信度（%）を添え、根拠の弱い判断を確定情報のように扱わない。
- **各要素の出自を問う。** 「目的から導出」か「成果物から相続」（過去実装・データ構造・テンプレの名残）か（正本: [ui-design/patterns.md](../ui-design/patterns.md) 原則 1）。「前からあった」「schema にあるから」「一覧にはよくあるから」しか根拠が出ない要素は惰性であり削除候補。過去の自分たちの決定（ブリーフ・計画）への忠実性も思考の代わりにしない。
- **指摘を削除指示と解釈しない（忖度反転の禁止）。** ユーザーやレビュアーが要素に疑問を呈したら、それは存在意義の説明要求であって削除指示ではない。忖度して即削除するのは、惰性で残すのと同型の思考停止。ゼロベースで再導出し、残す/直す/消すを自分の根拠で裁定する。
- **「問題なし」は正当な結論。** 監査は変更ノルマではない。指摘を捻り出さず、現状が最適ならそう報告する。
- **装飾を理由にしない。** 色帯、グラデーション、glass、shadow、巨大カードなどは、業務上の識別・導線・状態理解に寄与しないならアンチパターンとして扱う。装飾系の禁止項目そのものは、プロダクト側のデザインシステム定義（例: DESIGN.md 等の禁止リスト）があればそれを正本とする。
- **デザインシステム前提で見る。** domain component は作ってよいが、Button / Card / Dialog / Dropdown / Sheet / Table / Tabs / Input / Select 等の共通 primitive を再実装してはいけない。
- **操作可能性は装飾と並ぶ前提。** クリックできる要素は、視覚以外でも「何を操作するか」と「どう操作するか (キーボード到達)」が伝わる必要がある。
- **利用頻度で表現を分ける。** 高頻度/主目的は前面へ。低頻度/例外は段階開示、二次導線、確認導線へ。
- **引き算を先に考える。** 情報・バッジ・説明文・選択肢を足す前に、削る/隠す/弱める/並べ替える。
- **通常ケースと例外ケースを混ぜない。** リトライ、削除、復旧、詳細設定などは主動線と同じ面積・強度で置かない。
- **lint で機械検出済みの項目は再チェックしない。** raw HTML → primitive 強制ルール、指定外アイコンライブラリの import 禁止などプロジェクトの lint が全件捕捉している項目は、ui-review 同様、このスキルは lint が原理的に取れない領域に集中する。

## 手順

1. **対象と利用シーンを 1 行で特定**
   - 形式: `〈誰〉が〈いつ/どの業務で〉〈何を判断/実行する〉ための UI`
   - 利用シーンはコード・ルーティング・画面文言から推定し、確信が持てなければ推定である旨を出力に明示する
2. **デザインシステム逸脱を検出**（見た目軸）— raw HTML / 独自 primitive / headless ライブラリ直叩き / className で primitive を解体していないか
3. **LLM っぽい UI を検出**（見た目軸）— 装飾はデザインシステム定義の禁止リスト参照、カード乱用（bento 風の詰め込み・カードの入れ子）、情報の水増し、汎用テンプレ感
4. **視覚表現・状態表現の一貫性を検出**（見た目軸）— hover/focus/selected/disabled/loading/empty/error が token と primitive の意味に合っているか。primitive のソースと token 定義ファイルを開き、状態ごとの class が token の意味と一致するかで判定する
5. **主目的 / 副目的 / 例外を分ける**（動線軸）— 操作・情報を高頻度/主目的、中頻度/副目的、低頻度/例外に分類する
6. **利用シーンのアンチパターンを検出**（動線軸）— 低頻度操作の主動線化、全部並列、次アクション不明、disabled 理由不明などを checklist に照らす
7. **出力面・宛先を監査**（宛先軸、対象にエクスポート・帳票・通知があるとき）— リポジトリ内を `export|workbook|notification` 等のキーワードで検索して出力面の実体を探してから、出力面ごとに読み手を確定し、宛先混線・社内情報の漏出・内部語の露出・情報量ゼロの列を checklist に照らす
8. **修正方針を出す** — 見た目は primitive/token 準拠へ、動線は配置・強度・段階開示・CTA 条件・復旧導線の変更で示す（追加情報ではなく削る/隠す/移す/強弱の変更を優先する）。検出ゼロなら「問題なし」と明言する

## 重大度ルーブリック

- **High**: 業務判断を誤らせる・主動線を阻害する・デザインシステム定義の絶対回避リスト違反・primitive 再実装
- **Medium**: 一貫性欠如・惰性要素・段階開示の欠如
- **Low**: 軽微な表現・好みに近い提案

確信度は 90 以上=コード/実機から断定できる、70=実装事実+利用シーンの推測に依存、50=推測が主とし、50 未満の指摘は書かない（ux-check と共通の基準）。

## やってはいけないこと

- 「見栄えが寂しい」だけを理由にカード、メトリクス、バッジ、色帯を足す
- 装飾系アンチパターン（グラデーション/glass/過剰角丸/影 等）を安易に採用する（詳細はデザインシステム定義の禁止リスト参照）
- デザインシステムに primitive がある UI を独自実装する
- primitive のソースを読まずに className だけで状態を断定する
- 目的関数や利用頻度を置かずに「分かりやすい/分かりにくい」と言う
- 既存実装を前提に小さな文言修正だけで済ませる
- 主目的と例外操作を同じ強度で並べたまま、説明文で補う
- 「念のため全部表示」を安全策にする
- 「AI っぽい」「UX が悪い」を主観で終わらせる。必ず checklist のどの症状かに落とす
- ユーザー/レビュアーが疑問を呈した要素を、再導出せずに忖度で即削除する（疑問 = 説明要求であって削除指示ではない）
- 指摘ゼロを恐れて弱い指摘を捻り出す（「問題なし」は正当な結論）
- 未監査・未検証の既存成果物（過去に作ったエクスポートやテンプレ）を「正しい前提」として後続判断の基準に置く

## 全リポジトリスキャンモード（CI 起動用）

引数なしで呼ばれた場合、または「全リポジトリ」「全コードベース」「棚卸し」を対象とする指示の場合は、本節に従う。CI から呼ばれる場合は変更ファイル一覧を明示した diff スコープで呼ばれることが多い。その場合も検出観点と出力フォーマットは本節に従う（対象ファイルの列挙とサブエージェント分担の手順は呼び出し元の指示が優先され、検査対象は渡された変更ファイルのみに絞られる）。スキャン結果を GitHub Issue 本文等に貼り付ける前提の場合は、そのままの Markdown として成立するようフォーマットを厳守する。

### 対象範囲

- フロントエンドのソースディレクトリ配下の `*.tsx`（page / feature / component 相当のディレクトリ。プロジェクトの構成に合わせて対象パスを指定する）

宛先軸（エクスポート・帳票の実装ファイル）は CI スキャン対象外。手動起動時のみ手順 7 を適用する。

### 進め方

1. 対象ファイルを Glob で **完全に** 列挙する（部分サンプリングしない）
2. ディレクトリ単位でサブエージェントに分担させて並列に検出する。各ファイルで見た目軸・利用シーン軸の両方を検出する
3. 各検出は本 SKILL.md および [references/checklist.md](./references/checklist.md) のどのチェック項目に該当するかを必ず明記する
4. 確証が低いもの・主観の強い意匠論は指摘しない（false positive を出さないことを優先）

### 出力フォーマット

そのまま貼り付け可能な Markdown を返す。**回答全体を ``` で囲まないこと**（見出し・箇条書きが生 Markdown として読まれる）。ラベル・タイトル等のメタ情報を呼び出し元が固定値で付与する場合は、本文に含めない。検出 0 件のときは「検出一覧」セクション自体を省略し、`## サマリー` だけで終わる。

```
## サマリー

- 系統: ui-check（UI 見た目・利用シーンアンチパターン）
- スキャン対象: <対象パス> の page / feature / component (.tsx)
- スキャン対象ファイル数: <N>
- 検出件数: <合計件数>

## 検出一覧（優先度の高いものから）

### 1. `path/to/file.tsx:行`

- 系統: 本 SKILL.md / checklist.md の該当チェック項目名
- 該当コード（5 行以内で引用）:

    <ここだけ code fence で引用してよい>

- 推奨対応: <削除 / 既存 primitive に置換 / 配置変更 / 段階開示 / 情報の段階開示化 など、1 行>
- 根拠: <なぜアンチパターンと判断したかを 1〜2 行>

### 2. ...
```

引数: $ARGUMENTS
