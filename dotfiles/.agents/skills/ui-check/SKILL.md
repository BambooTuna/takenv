# UI Check Skill（見た目・利用シーン・ページ体験の統合監査）

## Purpose

UI/UX を検出専用で監査する。核心原則は 1 つ:

1. **全要素に存在意義の説明責任を課す** — 「誰が・どんな状況で・なぜそれを見るのか・何に使うのか」を説明できない要素（出自が「前からあった」「schema にあるから」だけの相続要素）は削除候補
2. **引き算を先に考える** — 追加ではなく削る/隠す/弱める/並べ替えるを優先する
3. **利用頻度・重要度で階層化する** — 主目的/高頻度は前面、副目的/低頻度は段階開示・二次導線
4. **検出専用** — 改善箇所と根拠の列挙まで。修正の実装は責務外（新規構図は [ui-design](../ui-design/SKILL.md)、実装後の総合レビューは [ui-review](../ui-review/SKILL.md)）。対象は画面に限らず、ユーザー・顧客の目に触れる成果物（エクスポート・帳票・通知文面）を含む

## モード

| | **コードモード**（旧 ui-check） | **ページモード**（旧 ux-check） |
|---|---|---|
| 対象 | コード差分・コンポーネント・CI スキャン | ページ全体・実機スクショ |
| 軸 | 見た目実装品質 + 利用シーン・動線 + 出力面宛先 | エンプラ SaaS 4 レンズで通し監査 |
| 出力 | 検出一覧 + 修正方針 | 改善箇所と理由の列挙のみ（修正はしない） |

判断に迷えば依頼文言（「UX」「エンプラ品質」→ページ、「デザインシステム逸脱」「独自実装」→コード）で判定する。

## You Must Read

- [references/checklist.md](./references/checklist.md) — 両モード共通の症状カタログ。必ず読む
- [../ui-design/patterns.md](../ui-design/patterns.md) — 情報設計原則の正本（ゼロベース・出自タグ / priority hierarchy / S/N / 動線重複の排除 / 宛先分離）。checklist はこの原則の症状カタログであり、解釈が割れたらこちらを正とする
- 対象コード/ページの実装、使用する共通 UI primitive（例: `<frontend-src>/components/ui/*.tsx`）。コードモードは `git diff`、ページモードは可能なら実機（ブラウザ操作ツールでシードデータ画面をスクショ、クリック完結経路のみ、type 入力は不可）。撮れなければ「コード読みのみ、実機未確認」と明示する

## 基本姿勢（共通）

- 既存 UI を出発点にしない。まず利用シーンと目的関数を言語化する。既存実装は制約ではなく仮説。各要素の出自を問う（目的から導出 か 成果物から相続 か）。判断には確信度（%）を添える
- 指摘を削除指示と解釈しない（忖度反転の禁止）。疑問 = 説明要求であって削除指示ではない。「問題なし」も正当な結論であり、指摘ゼロを恐れて弱い指摘を捻り出さない
- 装飾を理由にしない。色帯・グラデーション・glass・shadow・巨大カード等は、デザインシステム定義の禁止リストがあればそれを正本として判定する。domain component は作ってよいが共通 primitive（Button / Card / Dialog / Table 等）を再実装しない
- 利用頻度で表現を分ける。高頻度/主目的は前面、低頻度/例外は段階開示・二次導線。通常ケースと例外ケースを混ぜない
- lint で機械検出済みの項目（raw HTML → primitive 強制、指定外アイコンライブラリ import 禁止 等）は再チェックしない

## コードモード — 手順

1. 対象と利用シーンを1行で特定: `〈誰〉が〈いつ/どの業務で〉〈何を判断/実行する〉ための UI`
2. デザインシステム逸脱を検出 — raw HTML / 独自 primitive / headless 直叩き / className での primitive 解体
3. LLM っぽい UI を検出 — 装飾（禁止リスト参照）、カード乱用、情報の水増し、汎用テンプレ感
4. 視覚表現・状態表現の一貫性を検出 — primitive のソースと token 定義を開き、hover/focus/selected/disabled/loading/empty/error が token の意味と一致するか判定
5. 主目的/副目的/例外を高頻度・中頻度・低頻度に分類し、利用シーンのアンチパターンを checklist に照らす
6. 対象にエクスポート・帳票・通知があれば出力面・宛先を監査 — `export|workbook|notification` 等で実体を検索し、宛先ごとに読み手を確定してから宛先混線・内部語露出・情報量ゼロの列を checklist に照らす
7. 修正方針を出す — primitive/token 準拠、配置・強度・段階開示・CTA 条件・復旧導線の変更を優先（追加情報でなく削る/隠す/移す/強弱の変更）。検出ゼロなら「問題なし」と明言する

### 出力形式（コードモード）

```md
## UI Check — <対象>
### 利用シーン
- 〈誰〉が〈いつ〉〈何を判断/実行する〉ための UI
### 結論
- pass / changes-requested / block（1行理由）
### High / Medium / Low
- [デザインシステム / 視覚表現 / LLMっぽさ / 利用シーン・動線] <箇所>: <問題>（確信度: NN%）
  - なぜ問題か: / 推奨修正:
### 利用頻度・引き算・次アクション
- 主目的・高頻度 / 副目的・中頻度 / 例外・低頻度: / 削る・弱める・隠すべきもの: / ユーザーが次にすべきこと: / 迷う・誤操作する余地:
```

### 全リポジトリスキャンモード（CI 起動用）

引数なし、または「全リポジトリ」「全コードベース」「棚卸し」対象、あるいは CI から変更ファイル一覧の diff スコープで呼ばれた場合に適用する（この場合も検出観点・出力フォーマットは本節に従う）。対象はフロントエンドソース配下の `*.tsx`（page/feature/component 相当）。宛先軸（出力面）は CI スキャン対象外、手動起動時のみ手順 6 を適用する。

1. 対象ファイルを Glob で完全に列挙し（部分サンプリングしない）、ディレクトリ単位でサブエージェントに分担させて見た目軸・利用シーン軸を並列検出する
2. 各検出は本 SKILL.md / [checklist.md](./references/checklist.md) のどの項目に該当するかを明記する
3. 確証が低い・主観の強い指摘はしない（false positive を出さないことを優先）

出力はそのまま貼り付け可能な Markdown で、回答全体を ``` で囲まない。検出 0 件なら `## サマリー` のみで終える。

```
## サマリー
- 系統: ui-check（コードモード） / スキャン対象: <パス> / 対象ファイル数: <N> / 検出件数: <合計>
## 検出一覧（優先度の高いものから）
### 1. `path/to/file.tsx:行`
- 系統: 該当チェック項目名 / 該当コード（5行以内）: / 推奨対応: / 根拠:
```

## ページモード — 手順

対象ページを利用者の体験として通しで監査し、エンタープライズ向け SaaS として高品質な UX になっているかを評価する。AI コーディングは情報を詰め込む方向に流れやすい。本当に必要かを常に問い、削ることを第一に考える。**ゴールは改善箇所と理由の列挙まで。修正はしない。**

エンプラ SaaS 品質の 4 レンズ（詳細は [checklist.md](./references/checklist.md#ページモード---エンプラ-saas-品質レンズ)）: 業務効率 / 予測可能性・一貫性 / 信頼感 / 静かな画面。

1. 対象ページと利用シーンを1行で確定。引数で特定できなければユーザーに確認する
2. 実装と実機を見る。スクショは情報密度・視線の流れ・崩れまで批判的に読む
3. 軸1（存在意義）: 要素ごとに存在理由と出自（目的由来/相続）を記録し、説明できないものを改善候補に積む。粒度は操作可能要素と意味のある情報ブロック単位（装飾の一字一句は対象外）
4. 軸2（表現・階層）: 頻度×重要度で分類し、階層化・段階開示・非表示・別表現への置換の余地を積む
5. 4 レンズで通し読みして漏れを拾う。装飾は禁止リストと突合、動線重複（patterns.md 原則4）・宛先分離（原則6）も確認
6. 改善箇所と理由を列挙して終了。優先度は業務影響（主動線>副動線>例外系）×確信度で並べる。検出ゼロなら「問題なし」と明言する

### 出力形式（ページモード）

```md
## UX Check — <ページ名>
### 利用シーン
- 〈誰〉が〈いつ〉〈何を判断/実行する〉ためのページ
### 結論
- 1〜2行の総評
### 改善箇所（優先度の高いものから）
#### 1. <箇所>（確信度: NN%）
- 軸: 存在意義（引き算） / 表現・階層 / エンプラ品質（効率・一貫性・信頼感・静かさ）
- 問題: / なぜ問題か: / 改善の方向性:（削る/隠す/階層を分ける/別表現に置換 など。実装はしない）
### 存在意義の棚卸し
- 説明できる要素: <要素→理由> / 説明できない・惰性の要素: <要素→出自>
```

良い指摘/悪い指摘の対比例は [checklist.md](./references/checklist.md#良い指摘--悪い指摘の対比例) 参照。

## 重大度・確信度（共通）

- **重大度**: High=業務判断を誤らせる/主動線阻害/デザインシステム定義の絶対回避リスト違反/primitive 再実装、Medium=一貫性欠如・惰性要素・段階開示の欠如、Low=軽微な表現・好みに近い提案
- **確信度**: 90以上=コード/実機から断定できる、70=実装事実+利用シーンの推測に依存、50=推測が主。50未満の指摘は書かない

## やってはいけないこと（共通）

- 「見栄えが寂しい」だけを理由にカード・メトリクス・バッジ・色帯・情報を足す、「念のため全部表示」を安全策にする
- デザインシステムに primitive がある UI を独自実装する / primitive のソースを読まずに className だけで状態を断定する
- 目的関数・利用シーンを置かずに「分かりやすい/分かりにくい」「AI っぽい」「UX が悪い」と主観で言う。必ず checklist のどの症状かに落とす
- 主目的と例外操作を同じ強度で並べたまま説明文で補う
- 既存実装・過去の成果物を「正しい前提」として基準に置く（ゼロベースで導出する）
- （ページモード限定）改善箇所の列挙を超えてパッチ・コード変更まで出力する
