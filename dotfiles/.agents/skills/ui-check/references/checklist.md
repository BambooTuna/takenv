# UI Check Checklist

情報設計原則（ゼロベース・出自タグ / priority hierarchy・段階開示 / S/N / 動線重複の排除 / 宛先分離）の正本は [ui-design/patterns.md](../../ui-design/patterns.md)。本書はその原則を検出用の症状カタログに落としたもので、原則の解釈が割れたら patterns.md を正とする。

## 0. 判定原則

S/N・優先度階層（フラット vs 段階開示）・動線重複排除の原則は [ui-design/patterns.md](../../ui-design/patterns.md) が正本（冒頭参照の通り、解釈が割れたらそちらに従う）。ここでは検出判定に使う最小限の言い換えだけを置く。

- 目的に寄与しない装飾・視覚状態・独自 UI 実装、および利用シーンに合わない配置・強度は雑音として扱う。
- エンプラ SaaS では、派手さよりも読みやすさ・状態の判別・操作可能性・既存 primitive との一貫性・利用頻度に応じた強弱を優先する。
- まず利用シーンを置く。誰が、いつ、何を判断し、何を実行するのかが曖昧なまま UI を評価しない。
- 通常ケースと例外ケースを混ぜない。例外は主動線を乗っ取ってはいけない。

## 1. デザインシステム primitive 逸脱

### High

- **独自 primitive 再実装**: `CustomButton` / `MyDialog` / `ActionCard` 等がデザインシステム primitive の役割を置き換えている。→ 共通 UI primitive（`components/ui/*` 等） + variant / `className` での最小調整に置き換える。
- **headless ライブラリの直叩き**: app feature 側で Radix 等の headless UI ライブラリを直接 import。→ デザインシステム側の wrapper を用意する。
- **className で primitive を解体**: variant で表現すべきものを `className` の上書きで潰している（例: `Dialog` / `Sheet` の overlay・focus・close affordance を消す）。
- **操作要素の accessible name 欠落**: アイコンのみのボタン、`div` や行への `onClick`、Tooltip にしか操作名が無いコントロール。→ アイコンのみは `aria-label`、非ボタン要素は `Button` / `Link` に置換。
- **interactive 要素の入れ子**: `<Link>` の中に `<Button>` を入れる等。→ デザインシステム primitive は `asChild` 等の合成 API で外側の意味と内側の見た目を合成する。

> raw HTML 要素 → primitive 強制、指定外アイコンライブラリの import 禁止は lint で機械検出済みなら、ここでは再チェックしない。

### Medium

- **semantic token の意味違い**（SKILL.md 手順 4 の判定基準）: 成功していない状態に `status-success`、warning でない情報に `warning` を使う。
- **primitive composition の欠落 (a11y 以外)**: `DropdownMenuTrigger asChild`、`DialogTitle`、`aria-current` 等、合成 API の組み合わせ忘れ。

## 2. レイアウト / レスポンシブ

> 重大度目安: Medium 寄り（一貫性・可読性の欠如）。操作対象が分からず主動線を阻害するレベル（多重スクロールでの誤操作など）は High。

- **多重スクロール**: main, panel, table, modal がそれぞれ縦スクロールし、操作対象が不明。
- **長文/長い名前の破綻**: `min-w-0` / `truncate` / `line-clamp` / `overflow-auto` の設計がない。
- **状態でレイアウトが跳ねる**: hover、loading、badge 追加、error 表示で高さ/幅が大きく動く。
- **テーブルにすべきものをカードグリッドにする**: 比較・走査が主目的なのにカードが視線移動を増やす（詳細理解が主目的ならカード/パネルでもよい。目的関数で判断する）。

## 3. LLM がやりがちな見た目アンチパターン

> 重大度目安: 装飾（デザインシステム定義の絶対回避リスト）の直接違反は High。カード乱用・情報の水増し・汎用テンプレ感は Medium 寄り。

- **見た目先行（色帯・グラデーション・glassmorphism・過剰角丸・影・浮遊感）**: プロダクト側のデザインシステム定義（例: DESIGN.md 等の「AIっぽさ禁止リスト」）があればそれを正本とする。
- **bento / card 乱用**: 何でもカードに入れ、カード内カードや均質な 3 カラムにする。→ 走査は table/list、操作は toolbar、文脈は sidebar/header を使う。
- **情報の水増し**: 判断が不要なタイミングでの関係ないメトリクス追加、説明文過多、無意味なアイコン、AI sparkle の濫用。
- **汎用テンプレ感**: ありきたりな SaaS hero / landing 風、全部同じ青/紫/グレー、ダミーっぽいコピー（画面の業務に接続しない文言）。

## 4. 利用シーン / 目的関数

> 重大度目安: Medium〜High。優先順位・主副動線が決まらない根本原因になるため、実害（誤操作・判断ミス）に直結する場合は High。

- **利用者・業務シーン不在**: 「何をできるか」は説明されているが「誰がいつ何のために使うか」がない → UI が機能一覧になり、優先順位や主副動線が決まらない。
- **既存実装への差分編集モード**: 既存のカード/モーダル/2カラムにバッジ・説明文・状態表示を足すだけで、構造が目的関数に合っているかを検証していない。
- **機能説明を目的関数と取り違える**: 機能列挙に終始し、判断速度・誤操作防止・復旧性の最適化対象が定まらない。

## 5. 利用頻度 / 主副動線

> 重大度目安: High 寄り（主動線の阻害・誤操作に直結しやすい）。

- **低頻度操作が主動線と同じ扱い**: 追加/削除、作成/復旧、通常/例外が同じ面積・順序・強度で並ぶ。→ 高頻度/主目的を前面へ、低頻度/例外は折りたたみ・二次ボタン・確認導線へ。
- **例外ケースが通常ケースを汚染**: エラー復旧・同一条件での再実行・破壊的削除のために、通常時の CTA や説明が複雑になる。
- **主 CTA が「今やるべきこと」になっていない**: CTA ラベルが汎用的、変更なしでも押せる、または低頻度操作が primary。
- **順序が利用頻度と逆**: 低頻度の設定・既存項目・詳細情報が上にあり、高頻度の追加・選択・判断が下にある。
- **同じ機能への partial な複数経路**: インラインで一部編集でき、別モーダルで別の一部を編集できる（動線ごとに機能カバレッジが異なる）。

## 6. 情報優先度 / 引き算

> 重大度目安: Medium 寄り（一貫性欠如・惰性要素）。差分が埋もれて業務判断を誤らせる場合は High。

- **全部常時表示**: schema にある情報や選択肢を、重要度・頻度で分けず全部出す。
- **差分が埋もれる**: 変更されたものと変わっていないものが同じ見た目で、追加/削除/更新の結果が一覧から分からない。
- **説明文で構造の弱さを補っている**: 長い説明文を読めば分かるが、配置や強弱だけでは主目的が分からない。
- **見た目のための情報追加**: 寂しさを埋めるための件数、バッジ、メトリクス、説明カード。
- **引き算をミニマル化と取り違える**: 必要な差分や警告まで薄くし、結果として判断しづらくなる。
- **出自不明の相続要素**: 「前の実装にあった」「schema にあるから」「こういう画面にはよくあるから」以外に存在意義（誰が・いつ・何のために見るか）を説明できない要素。→ ゼロベースで再導出できなければ削除（[ui-design/patterns.md](../../ui-design/patterns.md) 原則 1 の出自タグ）。
- **件数かっこの惰性**: 全見出しに機械的に (n) を付ける。原則: スクロール・折りたたみで全体が見えなくなり得るリストにだけ件数を付ける。全件見えている見出しには付けない（番号付きリストなら末尾番号が件数）。
- **似た区分の分立**: 読み手には区別できない 2 つの入れ物が実装都合で並ぶ。→ 読み手の軸（例: 宛先が顧客か社内か）で統合・再分割する。

## 7. 次アクション / 状態 / 復旧

> 重大度目安: High 寄り（次の一手が分からない・復旧できないは業務判断を誤らせ主動線を阻害する）。

- **次に何をすればよいか分からない**: 空状態・変更なし状態・エラー状態・処理中状態でユーザーの次アクションがない。
- **disabled の理由が構造から分からない**: ボタンが押せないが、何を変えれば押せるか不明。
- **実行結果の予測ができない**: 選択やチェック変更後、何が追加/削除/更新されるか分からない。
- **復旧導線がない**: 間違えて外した/変更した時に元へ戻せない。
- **処理中に前回結果と新結果が混同される**: 生成中/更新中に古い結果が見えているが、そのことが明確でない。
- **エラー復旧と通常更新の条件が同じ**: 失敗後のリトライなのに変更が必須、または通常更新なのに変更なしで実行できる。

## 8. モーダル / フォーム / 選択 UI

> 重大度目安: Medium 寄り。破壊的/取り消しづらい操作が軽い扱いになっている項目は High。

- **モーダル内の主作業が見えない**: 開いた直後に、最もよくやる操作ではなく既存情報や説明が先に出る。
- **選択 UI が差分ではなく一覧管理になっている**: 更新モーダルなのに既存項目と追加候補が同じリスト/強度で並ぶ。→ 更新時は「変更対象」を中心にし、既存項目は必要時だけ見せる。
- **破壊的/取り消しづらい操作が軽い**: 削除・外す・上書き・リセットが通常チェックや primary CTA と同じ軽さ。→ 対象名・差分・確認・二次導線化・取り消し手段を用意する。
- **選択済み状態のラベルが過剰**: 全行に「使用中」「選択済み」等が並び、肝心の変更が埋もれる。
- **候補がない時の代替行動がない**: 「追加できる候補はありません」だけで終わる。

## 9. 出力面・宛先（エクスポート資料・帳票・通知など画面以外も対象）

原則の正本は [ui-design/patterns.md](../../ui-design/patterns.md) 原則 6（宛先分離）。出力面ごとに読み手を確定してから照らす。

> 重大度目安: 社内情報の漏出・内部語の露出は High（読み手を誤らせ、業務判断・信頼に直結）。列 / 表記の書式系（情報量ゼロの列・空値表現の不統一等）は Medium〜Low。

- **宛先混線（三人称ラベルの共用）**: 社内向け画面のラベル（読み手を「顧客」と三人称で呼ぶ文言等）を、その顧客本人が読む資料へ共通定数のまま出す。→ 宛先で表現が変わるラベルは共用せず出力面ごとにローカルに持つ。
- **社内宛て情報の漏出**: 裏取りメモ・懸念・交渉材料・社内論点・回避案候補が客先出力に出る。→ フィールド単位で宛先を決め、列 / 節ごと出さない。生値の非出力をテストで担保する。
- **内部語・システム都合語の露出**: 内部 ID・エイリアス（`[CP1]` 等）・「生成されていません」のようなシステム視点の文言が人間向け出力に出る。人間が見て分からないものの出力は禁止。
- **情報量ゼロの列（同文言の繰り返し）**: 判定列と対応方針列が全行で同じ語を繰り返す等、他列から導ける値だけの列。→ 差分情報を持たせるか列を消す。
- **全行で空・同値になる列 / 節**: モードや入力条件により契約上必ず空・同値になる列・シート・節を出したまま。→ 条件ごとに列 / シートごと省略する（空欄の羅列は「未完成の資料」に見える）。
- **数字の一人歩き**: 適合率のような単一集計値を、算出方法の注記（母数・重み付けの有無）や内訳なしで出す。→ 注記と内訳を併記する。
- **空値表現の不統一**: 同じ資料内で空欄・「—」・「なし」が混在する。→ 1 つに統一する。

## 10. デザインシステム primitive 監査で読むファイル

対象 UI が使う共通 UI primitive のソース（ボタン・カード・ダイアログ・ドロップダウン・シート・サイドバー・テーブル・タブ・入力欄・セレクト・テキストエリア等）を開いて確認する。プロジェクトの構成に合わせてパスを特定する（例: `<frontend-src>/components/ui/*.tsx`）。

対象 UI が使う primitive だけでよいが、className が最終的にどう合成されるかまでは確認する。

## 11. grep / rg の入口

```sh
# 見た目 / primitive
rg "Custom(Button|Card|Dialog|Modal|Select|Dropdown|Table)|My(Button|Card|Modal)|from '@radix-ui" <frontend-src>
rg "bg-gradient|from-|to-|via-|backdrop-blur|blur-\\[|rounded-2xl|rounded-3xl|shadow-lg|shadow-xl|shadow-2xl|border-l-2|border-l-4|before:left-0" <frontend-src>   # デザインシステム定義の禁止リストの機械的入口
rg 'size="icon"' <frontend-src>   # ヒット近傍に aria-label / aria-labelledby があるか確認
rg '<div[^>]*onClick' <frontend-src>   # 非ボタン要素の onClick (keyboard 不可)
rg '<Link[^>]*>\s*<Button' <frontend-src>   # interactive 入れ子 (asChild 推奨)
rg "件数|サマリー|インサイト|AI が|効率化|おすすめ|最新|完了数|最終実行" <frontend-src>   # 自社の禁止語彙・UI コピーのパターンに合わせて調整する

# 利用シーン / 動線
rg "整理し直す|再生成|選び直し|変更してください|ありません|未選択|選択済み|使用中|未使用" <frontend-src>
rg "disabled=|isExecuting|isProcessing|ERROR|PROCESSING|SUCCESS" <frontend-src>
rg "DialogTitle|DialogDescription|DialogFooter|SheetTitle|SheetDescription" <frontend-src>
rg "追加|削除|外す|戻す|リセット|キャンセル|再実行|最新版|履歴" <frontend-src>
```

grep 結果は疑いであって判定ではない。目的関数・利用シーンに照らして必要なら許容する。
