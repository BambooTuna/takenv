# Issue Triage

対象リポジトリの利用者・目的・現在の優先事項に沿って、issueを分類する。指定がなければopen issue全件を対象にする。

## 判断基準

| verdict | 意味 | 判断材料 |
| --- | --- | --- |
| `NOW` | 今やる | 利用者のブロッカー、重要機能の不具合、セキュリティ・データ破損の実害 |
| `NEXT` | 次のサイクル | 現在の目標に直結するが、今すぐでなくてもよい |
| `LATER` | 後回し | 価値はあるが現在の優先事項ではない |
| `DROP` | 閉じる候補 | 修正済み、重複、対象外、前提が失効したもの |
| `NEEDINFO` | 情報不足 | 再現手順や判断に必要な前提が不足 |

古さ・コメントの少なさ・再現できなかったことだけでDROPを確定しない。タイトルが似たissueも本文と期待動作を比較する。

## 手順

1. 対象repoと範囲、プロジェクトの優先事項、既存ラベルを確認する。
   ```bash
   gh issue list --state open --limit 200 --json number,title,labels,createdAt,updatedAt,author,comments,body
   gh label list
   ```
   取得上限に達したら上限調整またはページングし、未取得のissueを残さない。
2. issueの主張を現在のコード、関連PR、コミットと照合する。古いissueの調査を最近のコミットだけに限定しない。
3. 件数が多ければ独立したissueを読取専用のサブエージェントに分担する。対象issue、プロジェクトの判断基準、関連パスを渡し、`verdict / reason / action / confidence`と根拠を受け取る。分担できない環境では順次調査する。
4. 結果を下表で集約する。閉じる候補と不確かな判断は根拠を再確認し、検証できなければその旨を残す。
5. 既に承認された対象・操作は反映する。未承認の変更は、対象issue・ラベル差分・コメント案を示してから確認する。調査だけの依頼なら結果を報告して終了する。

| Issue | verdict | 根拠 | 推奨操作・コメント案 | 未確認事項 |
| --- | --- | --- | --- | --- |

## 反映

- `DROP`: `gh issue close <N>`。コメントを付ける場合は内容も依頼・承認の範囲に含める。
- ラベル変更: `gh issue edit <N> --add-label <label> --remove-label <label>`。変更のないフラグは省く。
- `NEEDINFO`: 必要な情報と質問案を示す。投稿を依頼・承認された場合にコメントする。

コメントは敬意ある短文とし、複数行なら本文ファイルを使う。新規ラベル、起票者へのメンション、title/body編集は必要性と依頼範囲を確認して扱う。
操作ごとの成否を記録し、最後に反映済み・失敗・未反映を簡潔に報告する。
