# テストアンチパターン

## 判定の本質（系統列挙より優先）

テストはコードに対して書くものではなく、プロダクトの背景・「なぜそれをやるのか」（= 仕様・業務ルール）に対して書くもの。よって無意味テストの根本判定基準は 1 つ:

> **このテストを削除したとき、検知できなくなる「仕様の破壊」を 1 文で言えるか。** 言えなければ無意味テストである。

以下の A〜D はこの基準に該当する既知の代表パターンであり、**網羅リストではない**。列挙に一致しなくても根本基準で無意味と判断できるものは、系統 `X`（列挙外）として検出する。その際は「削除しても何も検知できなくならない」ことの説明を根拠に必ず書く。逆に、列挙に形が似ていても根本基準で意味があるもの（例: プロンプト文言そのものがプロダクト仕様である場合の文言検証）は検出しない。

X で検出したパターンが繰り返し現れる場合は、本 SKILL.md に新系統として追記する（このリストは運用で育てる）。

---

## A. 実装と一体化したテスト

振る舞いを変えていないのに、内部実装を変えただけで壊れるテスト。リファクタしても外から見た振る舞いが同じなら本来テストは壊れてはいけない。

- **A-1. テスト対象を mock している**: テスト対象自身、またはその依存先を mock し、mock の戻り値を expect しているだけで、テスト対象のロジックが実行されていない（mock 内で本物と同じ処理を再実装しているだけの mock も同種）
  - 境界: 依存先を mock すること自体は A-1 ではない。テスト対象自身の分岐・変換・集約ロジックが実行され、その結果を expect していれば正当である。
  - A-1 に該当するのは、expect が mock の戻り値をそのまま確認しているだけで、テスト対象のロジックを通っても通らなくても結果が変わらない場合である。
- **A-2. 実装を expect にコピペしている**: 期待値が mock の戻り値・クエリ引数・定数の中身をそのまま書き写したもの。実装を丸ごと消しても mock/定数が変わらない限り通ってしまい、仕様の検証になっていない

## B. 外部仕様の再確認

自分が書いたロジックではなく、TypeScript / Zod / JS の言語・ライブラリが保証していることをテストしている。

- **B-1. `toHaveProperty` の並べ立て**: 値検証を伴わない存在確認だけの羅列
- **B-2. `typeof` 再確認**: 値 assert 直後に型を再確認しているだけで自明
- **B-3. `safeParse().success` のみの確認**: Zod のバリデーション成否だけを見て `data` の中身を未検証のまま
- **B-4. 必須項目への全プリミティブ型の網羅**: TypeScript の型システムが保証する範囲を手動で網羅している
- **B-5. 薄いラッパー関数への境界値網羅**: ロジックのない委譲関数に対して境界値テストを網羅している

repository の統合テスト（実 DB）は A-1 の対象外。B の判定は「独自のクエリ条件・マッピング・集計を検証しているか」で行い、ORM が保証するだけの挙動（単純な save→find の往復等）の確認は B に該当する。

## C. 検証宣言と検証の乖離

`it` 名で宣言した検証内容と、実際の assert が食い違っている。あるいはコメントで「検証しない」と自白している。

- **C-1. it 名が宣言する検証と assert の実体が食い違う**: 例えば `it('エラーを投げる')` と書きながら `expect(...).resolves` を検証している
- **C-2. コメントやテスト本文で「ここでは検証しない」と自白している**: 検証を放棄した箇所がテストとして残っている
- **C-3. 宣言に対して assert が空虚**: it 名やコメントで具体的な仕様（境界処理・値の変換・スキップ条件）を宣言しながら、assert は `toBeDefined()` / `not.toThrow()` / 呼び出し回数のみで、宣言した仕様が壊れても通ってしまう。宣言した値・状態そのものを検証していないテスト

## D. 重複（既存テストの焼き直し）

既存テストと実行されるコードパス・assert が実質同一で、差分がテスト対象の分岐に影響しない。

- **D-1. パラメータ違いに見えて同一パスの再実行**: 入力値だけ変えたが、その値が影響するロジックを mock で固定しているため、既存テストと全く同じ分岐しか通らない（例: 日付を変えたのに期限判定を `mockReturnValue(true)` で固定）。it 名だけ「境界値」等の新観点を謳っていれば C-1 も併発する
- **D-2. 同一 assert の別ブロック再掲**: 別の describe / テスト観点の中に、既存テストと同一の assert 一式がコピペされており、そのブロック固有の検証を足していない

D の判定は「既存テストを消してこのテストだけ残した場合と、このテストを消して既存テストだけ残した場合で、検知能力に差がないか」で行う。共通実装へ委譲している複数モデルの配線確認（別テーブル・別 schema への接続そのものを見る統合テスト）は D ではない。

## 個別レビューモード

特定ファイル・PR diff を対象とする依頼の場合、検出観点（A/B/C/D/X）と 1 検出あたりの出力構造は次節のスキャンモードと同じとする。対象は指定されたファイルのみに絞り、出力は Issue 用フォーマットに固定せず通常の返答でよい（サマリーの対象範囲行は、対象に合わせて書き換える）。検出 0 件のときは「検出なし」と明言する。スキャンモードの「0 件時はサマリーのみ」規定は Issue 用フォーマットの話であり、個別モードでは判断根拠を簡潔に添えてよい。

## 全リポジトリスキャンモード（CI 起動用）

引数なしで呼ばれた場合、または「全リポジトリ」「全コードベース」「棚卸し」を対象とする指示の場合は、本節に従う。CI から呼ばれる場合は変更ファイル一覧を明示した diff スコープで呼ばれることが多い。その場合も検出観点と出力フォーマットは本節に従う（対象ファイルの列挙とサブエージェント分担の手順は呼び出し元の指示が優先され、検査対象は渡された変更ファイルのみに絞られる）。スキャン結果を GitHub Issue 本文として貼り付ける前提の場合は、フォーマットを厳守する。

### 対象範囲

- リポジトリ内の `*.spec.ts` / `*.spec.tsx`（対象パッケージ・ディレクトリはプロジェクトの構成に合わせて指定する）

### 進め方

1. 対象ファイルを Glob で **完全に** 列挙する（部分サンプリングしない）
2. パッケージ / ディレクトリ単位でサブエージェントに分担させて並列に検出する
3. 各検出は本 SKILL.md の検出ルール（A-1 / A-2 / B-1〜B-5 / C-1〜C-3 / D-1〜D-2 / X）のどれに該当するかを必ず明記する。X の場合は「判定の本質」の根本基準（削除しても検知できなくなる仕様の破壊がない）の説明を根拠に含める
4. 系統照合だけで終わらせない。列挙パターンに一致しないファイルにも「判定の本質」の根本基準を適用する（列挙はショートカットであり検出範囲の上限ではない）
5. 確証が低いものは指摘しない（false positive を出さないことを優先）。基準は「引用コードだけを見た第三者が同意できないものは書かない」

### 出力フォーマット

GitHub Issue 本文としてそのまま貼り付け可能な Markdown を返す。**回答全体を ``` で囲まないこと**（見出し・箇条書きが生 Markdown として読まれる）。ラベル・Issue タイトル・workflow run URL 等のメタ情報は呼び出し元が固定値で付与する場合、本文に含めない。検出 0 件のときは「検出一覧」セクション自体を省略し、`## サマリー` だけで終わる（後段の起票判定は `### N.` 形式の検出見出しの有無で行うため、判定用マーカーや件数指定の追記は不要）。「検出一覧（優先度の高いものから）」の並び順は A-1 → A-2 → X → C → D → B の順、同系統内は同一ファイル内の件数が多い順とする。

```
## サマリー

- 系統: test-check（無意味テスト）
- スキャン対象: <対象パッケージ> 配下の *.spec.ts / *.spec.tsx
- スキャン対象ファイル数: <N>
- 検出件数: A=<N>, B=<N>, C=<N>, D=<N>, X=<N>（合計 <X> 件）

## 検出一覧（優先度の高いものから）

### 1. `path/to/file.spec.ts:行`

- 系統: A-1 / A-2 / B-1〜B-5 / C-1〜C-3 / D-1〜D-2 / X のどれか
- 該当コード（5 行以内で引用）:

    <ここだけ code fence で引用してよい>

- 推奨対応: <削除 / 振る舞い検証に書き直す など、1 行>
- 根拠: <なぜ無意味テストと判断したかの 1〜2 行>

### 2. ...
```
