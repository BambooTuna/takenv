# Test Review Skill

## Purpose

テスト項目（テストコード・テストケース一覧・テスト計画）が QA 観点で適切にカバーされているかをレビューするスキル。

AI 駆動開発ではテストコードを書くこと自体は容易になった一方、観点を渡さない限り「正常系中心の薄いテスト」になりやすい。
このスキルは、書かれたテストに対して **6 つの QA 技法** で網羅性を点検し、抜けている観点を具体的に指摘する。

> 出典: 「AI駆動開発時代に、おさえておきたいQA技法」（外山氏 / Zenn）

## 発動条件

- 「テストレビュー」「テスト観点」「テストの網羅性」「QA 観点」のような依頼
- PR にテストが含まれているが観点が薄いと感じたとき
- 新規実装のテストコード追加直後の自己レビュー
- バグ修正の回帰テストが十分かのチェック

## You Must Read

- レビュー対象のテストコード（ユニット / インテグレーション / E2E）
- 対象機能の仕様（issue / docs / コード本体）
- 関連 use case / repository / value object / state の定義

## 0. 前提整理（レビュー最初の必須ステップ）

**「実装ありきで網羅的にテストする」ことは目的ではない。** テストの目的は「実装の意図 / 受入条件 (AC) として宣言された境界を保証する」こと。
6 つの QA 技法に入る前に、必ず以下を箇条書きで明示してからレビューを始める。これを書けない / 書かないなら QA 技法の網羅性を議論しても無意味。

1. **なぜこの実装をやろうとしたか**: 解決したい課題 / バグの再発防止 / ユーザーストーリーを issue・PR description から引用する
2. **実装の目標（受入条件 / AC）**: 「この条件が満たされれば完成」と言える境界を列挙する
3. **保証したい境界の一覧**: AC を技術的に書き直したもの（例: 「上限 50 件を超えたら reject」「IN_PROGRESS → COMPLETED は禁止」）
4. **保証しなくてよい範囲（Out of Scope）**: AC に含まれない仕様を明記し、過剰テストを牽制する

この 4 項目を `Findings` 表より前に提示すること。AC / issue が見当たらない場合は、次の 3 段階で対応を分ける:

- **(a) AC 相当の記述が確定している**: issue / PR description に AC 相当の記述が箇条書きで存在する → 通常レビューへ進む
- **(b) AC は明文化されていないが目的が推定できる**: PR description・コード・テスト名から目的が推定できる場合、**推定 AC を【推定】ラベル付きで自分で列挙して提示し、それを前提に限定レビューを行う**。推定 AC を確定仕様のように扱わず、`Follow-up` に AC 確定要請を必ず入れる
- **(c) 目的自体が読み取れない**: 「**仕様不明確のため、テスト追加より先に AC 確定が必要**」と返し、レビューを止める。この場合 `Findings` 表は出さず、前提整理 4 項目のうち書けた部分と「何が分かれば再開できるか」だけを返す

## レビュー観点（6 つの QA 技法）

### 1. 同値分割
入力値を「同じ扱いになるグループ」にまとめ、代表値でケースを構成する（同一グループ内の冗長なケース重複は逆に指摘）。
- 例: 入力候補一覧 → `対象条件を満たす / 種別不一致 / 前処理未完了 / 別スコープ / 存在しない id` のグループ × 各代表値

### 2. 境界値分析
`>= / >`、`<= / <` の取り違えを拾える境界値（下限-1 / 下限 / 上限 / 上限+1）を最低限押さえているか。
- 例: 上限が N 件の仕様なら `0, 1, N, N+1` を必ず含む

### 3. デシジョンテーブル
複数条件の組み合わせを伴う仕様で、AND/OR の組み合わせ網羅が崩れていないか（1 条件ずつの単発テストで済ませていないか）。
- 例: 複数の前提生成の完了有無 × 入力選択の妥当性のような複合条件（一部の前提は任意（null 許容、指定時のみ完了必須）等の条件分岐に注意）

### 4. 状態遷移テスト
状態を持つ機能で、**許可される遷移** と **禁止される遷移** の両方をテストしているか。
- 例: `PENDING → PROCESSING → SUCCESS / FAILED → PROCESSING (retry)` のような処理状態遷移で、`PROCESSING` / `SUCCESS` での再 trigger は CONFLICT として拒否されるか
- 例: 生成系の世代管理で `PROCESSING → SUCCESS / ERROR` の一方向遷移のみ許可し、再生成は新世代作成として扱われるか。二重実行ガードの単位（対象エンティティ単位か、より広い単位か）が実装と一致しているか
- 対象プロジェクトの状態遷移図は実装（enum と遷移ガード。多くの場合 enqueue 側の use-case にある）を必ず正として確認し、ドキュメントや過去の記憶とズレていれば実装を正とする
- 状態ごとの単発テストだけで遷移のバリデーションが抜けていないか

### 5. エラー推測（実運用で壊れやすいパターン）
- 二重送信 / 戻る操作後の再送
- タイムゾーン差分（`createdAt` / `updatedAt` 周辺）
- 空文字 / null / undefined の混在
- 全角半角混在 / 改行コード差分
- 権限の抜け道（org membership / role / cross-tenant）
- 通信失敗時の中途半端な状態（部分書き込み、トランザクション境界）
- atomic 更新の race（既存値ありでスキップする更新など）
- TOCTOU / 二重実行（PROCESSING 中の再 trigger）
- 外部ワークフロー（LLM 呼び出し等）のトリガー失敗時の状態不整合（trigger 失敗で世代を ERROR 確定するか）
- 成功表示と実データのズレ

### 6. チェックリスト（層別）
- **Unit**（pure function / value object / use case）: 正常系 / 異常系 / 境界値
- **Integration**（repository / Server Action）: DB 状態を含む組み合わせ、トランザクション境界、 楽観的ロック
- **UI**（Server Action 呼び出しコンポーネント）:
  - バリデーションエラー表示
  - ローディング中の二重送信防止
  - 権限がないユーザーへの非表示
  - Server Action 失敗時の UI（safe-action のエラー表示）
  - console error / type error が出ていない

## Hard Constraints

- **テストの存在意義を実装ではなく AC / 仕様に紐づける**。各テストが「どの AC / 仕様分岐を保証するためにあるか」を説明できない場合、削除 / 統合候補として指摘する（実装ミラーのテストは価値が低い）。実装ミラーの体系的検出（mock 写像・expect コピペの判定）は test-check skill の責務。本 skill では AC に紐づかないテストとして削除/統合提案するに留め、mock 構造の詳細分析には立ち入らない
- **実装網羅率 (line / branch coverage) を埋めるためだけのテストは認めない**。AC に存在しない分岐を埋めるテストは `major gap` の逆 = **過剰テスト** として指摘する
- **テストを「増やす」より「意図に揃える」を優先する**。Findings は件数ではなく、AC 境界に対する漏れ / 過剰の両方を扱う
- 既に書かれているテストの正常系を肯定的に再評価しない。**観点の漏れにフォーカスする**
- AI が生成しがちな happy path 偏重に流されない
- テストコードを直接書き換えない。指摘ベースで返す（実装は Implementer に委ねる）
- 「壊れそう」だけの感覚的指摘で済ませず、必ず **QA 技法名でラベリング** する
- 仕様自体が曖昧な場合、テスト追加より先に **仕様の明確化** を要求する
- プロダクトの現行スコープ外の観点をでっち上げない（MVP スコープ・過去仕様の残置物など、プロジェクトの CLAUDE.md やスコープ定義があればそれに従う）

## Output Format

### Findings

| # | 技法 | 重大度 | 紐づく AC / 仕様 | 観点 | 抜けているケース / 過剰ケース | 推奨追加テスト or 削除提案 |
|---|------|--------|------------------|------|----------------------------|--------------------------|

- `紐づく AC / 仕様` 列が **空欄になる Findings は存在理由を疑う**。AC に紐づかない指摘は「観点を増やすための観点」になっており、レビューしない方が良い
- 既存テストが AC に紐づかない場合は `観点` 欄に「実装ミラー / AC 不在」と書き、`推奨追加テスト or 削除提案` 欄に **削除 or 統合の提案**を書く
- `抜けているケース` だけでなく `過剰ケース` (= AC に存在しない分岐を埋めるテスト) も同じ表で扱う

#### 重大度の閾値（迷ったら高い側に倒す）

- `critical`: マージブロック必須。仕様の主要分岐、cross-tenant guard、認可、データ取りこぼし／二重取得、状態の禁止遷移など事故直結の観点が完全に抜けている
- `high`: マージ前に埋めるのが望ましい。`>= / >` 取り違えを拾える境界値、状態の `partial` / 禁止遷移、外部 API（LLM Workflow 等）失敗時の継続性など
- `medium`: 後続 PR でも良いが横展開で増幅するリスクあり。集計値の合算、順序保証、組み合わせ網羅、silent skip 仕様化
- `low`: 観点として固定したいが運用上の発生確率が低い。極端値、参照同一性、Invalid Date 等

「直感で high / 直感で low」だけで決めず、上記キーワードを 1 つ引用して理由付けすること。

**書き方**: 重大度欄に `high (境界値の取り違え)` のように括弧書きでキーワードを併記する。観点欄には根拠の本文を書き、重大度欄は「ラベル + キーワード」の形に固定する。

#### 技法のオーバーラップ時の選択

技法が重複したら次の優先で 1 件 1 技法に割り当てる:

- 数値パラメータの上限・下限・取り違えを問う → **境界値分析**（`>= / >` まで踏み込めるため、同値分割と被ったらこちらに寄せる）
- 入力値を「まとまりの代表値」で減らす（境界に絡まない）→ **同値分割**
- 複数条件の AND/OR 真理値表 → **デシジョンテーブル**
- ステータス遷移の許可・禁止 → **状態遷移テスト**
- 過去事故・運用クセに基づく抜け → **エラー推測**
- 層別の雛形（正常系・loading・権限・通信失敗）の漏れ → **チェックリスト**

#### 仕様不明確な観点の扱い

実装の挙動は読めるが「それが仕様として正しいか」が docs / issue から確定できない場合:

- 技法欄: 推定された技法名 + ` (仕様不明確)` を併記（例: `状態遷移テスト (仕様不明確)`）
- 推奨追加テスト: 「仕様 A なら ... / 仕様 B なら ...」を併記し、確定前にテストを書き切らない
- **Follow-up に仕様確定要請を必ず追加する**（test-review skill では仕様を勝手に決めない）

#### Findings 件数の目安

- 1 ファイルにつき **3〜10 件** を目安に絞る。観点漏れの羅列ではなく、優先度の高い順に並べる
- 複数ファイルの PR では表は PR 全体で 1 つにまとめ、合計 5〜15 件を目安に絞る（ファイル数 × 10 に膨らませない）
- それ以上発見した場合は 11 件目以降を `Follow-up` 節に「次に見るべき観点」として箇条書きで逃がす（Findings 表は読まれることが価値）

### 追加推奨テストケース

そのままテストコードに落とせる粒度で:

```
describe(...) {
  it("境界値: 上限+1 のとき XX エラーになる", ...)
  it("不正遷移: COMPLETED から cancel はエラー", ...)
}
```

### 全体評価

- `approve` — AC に紐づく境界がすべてテストで保証されている。実装ミラー / 過剰テストも無い
- `minor gap` — 追加 or 削除推奨だが MVP リリースは止めない
- `major gap` — 以下のいずれかに該当する場合に倒す:
  - AC / 仕様で宣言された境界が複数欠落している
  - 仕様の抜けがあり、再設計レベルの追加が必要
  - **テストの大半が AC に紐づかない実装ミラー** になっており、何を保証しているか説明できない（= テストを書くこと自体が目的化している）

### Follow-up

- 仕様 docs に追記すべき内容
- 横展開すべき観点（同種機能で同じ抜けがありそうなら指摘）

## レビュー時の言い換え（AI への再依頼テンプレート）

レビュー結果から、Implementer / AI に追加テストを依頼する際は次の形を推奨する:

```
以下の観点で <対象機能> のテストを追加してください。

- 同値分割: <代表値のグループ>
- 境界値: <具体的な値リスト>
- デシジョンテーブル: <組み合わせ表>
- 状態遷移の禁止ケース: <禁止遷移リスト>
- エラー推測: <事故パターン>
```

「テストを追加して」だけでは正常系が増えるだけになりがちなので、**技法名と具体値を必ず添える**。
