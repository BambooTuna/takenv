# UX Check Skill（ページ単位の UX 監査 — エンプラ SaaS 品質）

## Purpose

対象ページを **利用者の体験として通しで** 監査し、エンタープライズ向け SaaS として高品質な UX になっているかを評価する。

AI によるコーディングは「情報をとにかく詰め込む」方向に流れやすい。それでは質の高い、差別化できるプロダクトは作れない。本当にその情報は必要かを常に問い、削ることを第一に考える。本当に必要なものはその理由が説明でき、納得できるものになっているはずで、そういうものだけを残す。

**ゴールは改善箇所とその理由の列挙まで。** 修正はこのスキルの責務外。修正に進む場合は、通常フロー（ui-design で構図 → 実装 → ui-review で点検）を別途回す。

## 位置づけ（関連スキルとの分担）

| スキル | タイミング | 対象 | 出力 |
|---|---|---|---|
| [ui-design](../ui-design/SKILL.md) | 実装前 | 画面の構図 | 目的関数・構図・引き算方針 |
| [ui-check](../ui-check/SKILL.md) | 実装後 / CI | コード・コンポーネント単位の症状検出（デザインシステム逸脱・LLM っぽい見た目・動線含む） | 検出一覧 + 修正方針 |
| [ui-review](../ui-review/SKILL.md) | 実装後 | 変更差分の総合点検（コード演繹） | pass / changes-requested |
| **ux-check（本スキル）** | 任意 | **ページ単位の体験全体** | **改善箇所と理由の列挙のみ** |

ui-check がコードから症状を拾う検出器なのに対し、ux-check は「このページは業務の道具として上質か」をページ丸ごとで問う。原則の正本は [ui-design/patterns.md](../ui-design/patterns.md)。解釈が割れたらそちらを正とする。

## You Must Read

- [../ui-design/patterns.md](../ui-design/patterns.md) — 情報設計原則の正本（ゼロベース・出自タグ / priority hierarchy / S/N / 動線重複の排除 / 宛先分離）
- プロダクト側のデザインシステム定義ドキュメント（例: DESIGN.md 等、装飾・見た目の禁止リストを定めたファイル）があれば参照する。無ければ本スキルの一般原則のみで判定する。
- 対象ページの実装（page / feature / 使用 primitive）
- 可能なら実機のページ。ブラウザ操作ツールでシードデータのある画面を開き、スクショで実際の情報密度・視線の流れを確認する（クリック完結経路で。type 入力は不可）

## エンプラ SaaS の品質基準（監査のレンズ）

対象は「業務で毎日使う習熟ユーザー」。コンシューマ向けの派手さや初見の驚きではなく、以下を高品質とする。

1. **業務効率** — 主目的の判断・操作に最短で到達できる。スキャン速度、クリック数、視線移動の少なさ。説明過多・オンボーディング的な冗長さは習熟ユーザーにはノイズ
2. **予測可能性・一貫性** — 同じ意味の操作は同じ場所・同じ語彙・同じ表現。画面間で流儀が揺れない
3. **信頼感** — データ量が現実的に増えたとき（長文 / 0 件 / 数百件）に破綻しない。破壊的操作に安全弁があり、いま何が保存されている状態かが分かる
4. **静かな画面** — 装飾でなく情報の構造で語る。目立たせるのは目的上「最初に見るべきもの」だけ

## 監査の 2 軸

### 軸1 — 要素の存在意義（引き算）

いま画面にある要素への疑義。全要素に存在意義の説明責任を課す。

- 「誰が・どんな状況で・なぜそれを見るのか・何に使うのか」を全要素について説明できるか。説明できない要素、説明が「前からあった」「schema にあるから」「一覧にはよくあるから」しか出ない要素は惰性であり削除候補
- 出自を問う: その要素は **目的から導出** されたか、**成果物から相続**（過去実装・データ構造・テンプレの名残）されたか
- 本当に必要なものは理由が説明でき、納得できるはず。そういうものは残してよい

### 軸2 — 表現・配置・階層

余計な要素が無くなっただけでは UX が良いとは言えない。残す情報の **表現方法** に改善の余地がないかを問う。

- 情報には利用頻度・重要度・見る人が必要とするタイミングの違いがある。それらを同じ強度で並べず、階層を分けているか（表に出す / 折りたたむ / 遷移先に置く / hover や詳細パネルに逃がす）
- **あえて表示しない** ことで重要なものを目立たせる、という選択を検討したか。全部見せるのは安全策ではなく設計放棄
- 表現の型（テーブル / タブ / 左右カラム / モーダル / インライン…）はその目的に対して他より優位と言えるか。「現状の表現を別の表現に置き換える」選択肢を必ず一度検討する
- これらはプロダクトの方向性・場面にもよる。判断基準は常に「目的関数に対して S/N が上がるか」であって、ミニマルさ自体ではない

## 手順

1. **対象ページと利用シーンを 1 行で確定** — `〈誰〉が〈いつ/どの業務で〉〈何を判断/実行する〉ためのページ`。引数でページが特定できなければユーザーに確認する
2. **実装と実機を見る** — コードを読み、可能ならブラウザ操作ツールで実ページのスクショを撮る。スクショは「撮るだけ」でなく情報密度・視線の流れ・markdown 崩れまで批判的に読む。撮れなければ「コード読みのみ、実機未確認」と出力に明示する
3. **軸1: 全要素の存在意義を棚卸し** — 要素ごとに存在理由と出自（目的由来 / 相続）を記録し、説明できないものを改善候補に積む。粒度は操作可能要素（ボタン・リンク・入力）と意味のある情報ブロック（見出し・カラム・バッジ・説明文）単位。装飾の一字一句までは対象外
4. **軸2: 表現・配置・階層を評価** — 頻度 × 重要度で分類し、階層化・段階開示・非表示・別表現への置換の余地を改善候補に積む
5. **エンプラ品質基準に照らす** — 業務効率 / 一貫性 / 信頼感 / 静かさの 4 レンズで通し読みし、漏れを拾う。装飾の疑義はデザインシステム定義の禁止リストと突合する（静かさ）。同じ目的への入口が複数ないかを見る（動線重複・patterns.md 原則 4、一貫性）。エクスポート・通知が絡めば宛先分離を確認する（patterns.md 原則 6）
6. **改善箇所と理由を列挙して終了** — 各指摘に「どの基準・原則に反するか」と確信度（%）を添える。確信度は 90 以上=コード/実機から断定できる、70=実装事実+利用シーンの推測に依存、50=推測が主とし、50 未満の指摘は書かない。優先度は業務影響（主動線への影響 > 副動線 > 例外系）× 確信度で並べる。修正はしない。検出ゼロなら「問題なし」と明言する

## 出力形式

```md
## UX Check — <ページ名>

### 利用シーン
- 〈誰〉が〈いつ/どの業務で〉〈何を判断/実行する〉ためのページ

### 結論
- 1〜2 行の総評（エンプラ SaaS としての現在地）

### 改善箇所（優先度の高いものから）

#### 1. <箇所>（確信度: NN%）
- 軸: 存在意義（引き算） / 表現・階層 / エンプラ品質（効率・一貫性・信頼感・静かさ）
- 問題: <何がどうなっているか>
- なぜ問題か: <どの基準・原則に反するか。利用シーンに紐づけて>
- 改善の方向性: <削る / 隠す / 階層を分ける / 別表現に置換 など 1 行。実装はしない>

#### 2. ...

### 存在意義の棚卸し
- 説明できる要素: <要素 → 1 行の存在理由>
- 説明できない・惰性の要素: <要素 → 出自>
```

### 良い指摘 / 悪い指摘の対比例

- 良い例: 「ステータス列: 全 8 状態が同じ Badge 強度で並び、業務上唯一の判断材料である『要対応』が埋没（軸2、確信度 85%）→ 要対応のみ強調し他は淡色化」
- 悪い例: 「情報が多く分かりにくい（どの要素が・誰にとって・なぜかが無い）」

## やってはいけないこと

- **修正まで進める** — このスキルのゴールは列挙まで。パッチ・コード変更を出力しない
- 指摘ゼロを恐れて弱い指摘を捻り出す（「問題なし」は正当な結論。監査は変更ノルマではない）
- ユーザーが疑問を呈した要素を、再導出せずに忖度で即削除候補にする（疑問 = 説明要求であって削除指示ではない）
- 引き算を「無差別にミニマルにすること」と取り違える（S/N を上げるのが目的。信号は立てる・誇張することもある）
- 目的関数・利用シーンを置かずに「分かりやすい / 分かりにくい」と主観で言う
- 「見栄えが寂しい」を理由に情報・装飾・カードの追加を提案する
- 確信度を添えず、根拠の弱い判断を確定情報のように書く
- 既存実装・過去の成果物を「正しい前提」として基準に置く（ゼロベースで導出する）
