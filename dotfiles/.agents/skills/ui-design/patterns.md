# UI 情報設計原則

[SKILL.md](./SKILL.md) の Step 2 (構図) と Step 3 (引き算) で、構造をどう組むか・何を見せ何を defer するか・どこに動線を引くか を決める時の判断原則。**このファイルが情報設計原則の唯一の正本**（プロジェクトのフロントエンド規約ドキュメントがあれば、そこから参照される想定）。

ここは **表現パターン (Modal / Sheet / Tab / Inline / Accordion 等) に依存しない一般原則** を固定する場所。特定の表現の使い分けは原則の適用例として下部にカタログする。判断に迷ったら、まずここを読む。

## 適用タイミング

- UI コンポーネントの新規実装・大きな書き換え
- 新しい画面 / コンポーネントの構図を組む時
- 既存画面の構造 (情報配置 / 動線 / 段階開示) を見直す時
- 「全部見せる vs あえて分ける」「並列で並べる vs 階層化する」「常時表示 vs 段階開示」のどれを採るか判断する時
- 「業界実例ではこう」「既存実装はこう」「これはアンチパターン」と言いたくなった時 (= 一度立ち止まる)

## 原則

### 1. ゼロベース思考 (既存実装と業界実例をしがらみにしない)

構図の出発点は **「既存実装にあるもの」ではなく「目的関数」**。

- 「既存に X があるから残す / 維持する」は思考の幅を狭める。**偶然の最適でなければ採用根拠にならない**
- 業界実例 (Linear / Notion / Stripe / Slack / Jira 等) は参考にしていいが結果論であって出発点ではない
- 「業界主流だから」「他のサービスでこうだから」を判断の最終根拠にしない
- 単一サービス / 単一文献を「業界主流」として一般化しない
- 既存画面・既存成果物を監査する時は、各要素に **出自タグ** を付ける: **目的から導出**（目的関数から今でも導ける）か、**成果物から相続**（過去の実装・データ構造・テンプレ・以前のレイアウトの名残）か。相続タグの要素は「誰が・いつ・何のために見るか」をゼロベースで再導出できない限り削除候補。「schema にあるから」「前からあったから」は出自の説明であって存在意義の説明ではない
- 過去の自分たちの決定（ブリーフ・canvas・計画文書）も相続の一種。忠実性を思考の代わりにしない。再検証した上でならズレてよく、実装側が正になることもある

### 2. Priority hierarchy で構造を決める (フラット vs 階層的隠蔽)

情報に優先順位の差があるかどうかで、**並列に並べるか / 階層的に defer するか** が決まる。これは Modal / Sheet / Tab / Accordion / 別画面遷移など個別の表現の **手前で** 下す判断。

| 設計 | 適する場面 | 強み | 弱み | 言外メッセージ |
|---|---|---|---|---|
| フラット (全並列) | 全て同等の重要度 / 上から順に読まれる | 一覧性 / 学習コスト 0 | 全部同強度 = priority が消える / スクロール疲れ | 「全部同じ重要度」 |
| 階層的隠蔽 (Progressive Disclosure) | primary と secondary が分かれる | priority が構造で伝わる / S/N が上がる | 切替コスト / 初見時の発見性低下 | 「A が中心、他は補助」 |

**どちらが優れているかは priority hierarchy の有無で決まる。**

- 同じ階層 (= 全部 primary) → フラット
- 階層がある (= primary と secondary が分かれる) → 段階開示

「全部見せる」「全部常時表示する」は意図的に選んだのでなければ **設計判断の放棄** になりがち。「情報を持っていればいるほど良いのは LLM だけ」で、人間の認知資源は有限。

「タブはアンチパターン」という主張に確立した根拠は **存在しない**。逆に Progressive Disclosure の手段として一般に支持されている。これは Modal / Sheet 等の他の defer 手段にも同じ理屈が当てはまる。

### 3. メリハリで視線と意味を作る (S/N を上げる)

priority hierarchy が決まったら、視覚表現で **強度差** を作る。同強度の並列は priority を消す。

- 表現の道具: 太字 / 文字サイズ / 余白 / 区切り線 / 色 / 配置 (上下左右) / アイコン / 図形量 / 動きの有無
- 視線誘導: 目的関数上「最初に見るべきもの」へ最も強い signal を当てる
- 信号は **足す方向**: 弁別すべき差はむしろ誇張する (前注意的処理に乗せる)。例: 「有/無」を一目で見たいなら ● と ・ の大小差は大きく取る
- 雑音は **引く方向**: 装飾・冗長ラベル・「念のため」表示・不揃いな器 (行高 / セル幅のばらつき)・不随意発火 (一覧スキャン中に開くホバー詳細)

引き算の本質は「無差別なミニマル化」ではなく **目的関数に照らして S/N を上げる** こと。信号を **足すこと** も含む。

### 4. 同じ機能への複数経路を partial に提供しない (動線重複の排除)

最も避けるべきアンチパターン。表現に依存しない一般則。例:

- 詳細パネルで編集できる + 別パネル / Sheet で **一部だけ** 編集できる
- インライン編集ボタンが多数 + ヘッダ「…」メニューにも「全体編集」がある
- 一覧から開く詳細と、別タブから開く詳細でカバレッジが違う

ユーザーは「同じことをしようとして UI が違う」「どの動線にどの機能があるか分からない」という認知負荷を負う。

**判断原則**: 同じ機能は **1 動線に絞るか**、複数経路を持つなら **完全に同じカバレッジ** にする。partial drawer / partial menu は最悪の組合せ。

### 5. 文献・業界実例を opportunistic に引用しない

理論や実例を自分の結論に都合よく解釈しない。これは表現選択以前の **議論の作法**。

- **Cognitive Load Theory (CLT) は「タブを否定する」根拠ではない**。CLT は逆に「secondary を隠して primary に集中させる」ことを支持する
- 「業界主流」「authoritative source」と書く前に **原典を確認** する。表面的な name-drop は逆効果
- 「アンチパターン」と断定する前にそれを支持する文献を確認する
- 引用するなら反対例 (= 別のパターンを採る主要サービス) も併記する

### 6. 宛先で文言と情報を分ける (読み手が違う出力面を共用しない)

同じデータが複数の出力面 (画面 / エクスポート資料 / 通知 / メール) に出る時、**出力面ごとに読み手を先に確定** し、文言・情報の取捨をその読み手に合わせる。「画面で見たい情報とエクスポートしたい情報は違う」— 包含関係を確認せずに同じ投影を使い回さない。表現パターン以前の一般原則。

- **読み手を三人称で呼ばない**: 社内向け画面の「顧客側に対応がない標準」のようなラベルを顧客本人が読む資料に出すと、読み手を三人称で呼ぶことになる。宛先で表現が変わるラベルは共用せず、出力面ごとにローカルに持つ (共通定数に寄せることを DRY と勘違いしない)
- **宛先 = 社内の情報は客先出力に絶対に出さない**: 裏取りメモ・懸念・交渉材料・社内論点・回避案の候補。フィールド単位で宛先を設計時に決め、出力側は列 / 節ごと出さない (値の一部マスクで済ませない)。テストで生値の非出力を担保する
- **内部語・システム都合語を人間向け出力に出さない**: 内部 ID・エイリアス ([CP1] 等)、「生成されていません」のようなシステム視点の文言。人間が見ても分からないものの出力は禁止
- **読み手の語彙で書く**: その読み手 (顧客・取引先・営業) がその用語を聞いて理解できるかを問う。実装都合・社内都合の区分を読み手向けの区分として流用しない

## 表現パターンの例示 (適用例カタログ)

ここから下は上記原則の **具体的な適用例**。原則を満たすなら、ここに無い表現 (タイル / ツリー / カンバン / マトリクス / オーバーレイ / プレビュー / フォーカスモード 等) を採っていい。**ここに書いた具体例が万能ではない**。原則 1〜5 に立ち返って優位性を言えるかで判断する。

### Modal (Dialog) / Sheet (Drawer) / Inline / Full-page の使い分け

判断軸: **親画面の情報を見続けたいか / 一旦遮断したいか / 文脈ごと切り替えたいか** (= 原則 2 の priority hierarchy の細分)

| パターン | 親画面の扱い | 適用場面 | 業界実例 (反対例も併記) |
|---|---|---|---|
| Inline | コンテキストの中で完結 | 1 フィールドの軽量編集 | Notion / Linear のフィールド ↔ 重い編集を Full-page にする Stripe |
| Sheet (Drawer) | 見続けられる (半分被るが視認できる) | 中〜長尺タスクで親画面の情報を参照したい | Stripe 新規 customer / GitHub Issue side panel ↔ Slack はチャンネル作成を Dialog |
| Dialog (中央 Modal) | 完全に遮断 | 短尺タスクで親画面と切り離して集中させたい | Slack チャンネル作成 / Figma プロジェクト移動 ↔ Linear は inline 中心 |
| AlertDialog | 完全に遮断 + 警告色 | 破壊的決定 (削除確認・データ消去) | 各種「本当に削除しますか?」 |
| Full-page navigation | 別画面に遷移 | 重いフォーム / 別文脈 / 集中タスク | Notion ページ open / Stripe checkout |

#### よくある誤解 (= 過去のセッションで定着済みの訂正)

- 「Modal は削除専用」は **誤り**。AlertDialog (Modal のサブ種) が削除に使われる。Modal (Dialog 全般) はもっと広く使える
- 「Sheet は新規追加専用」は **誤り**。Sheet は万能パターンで、固定の用途はない
- 「タブはアンチパターン」を支持する authoritative source は **存在しない**。逆に Progressive Disclosure の手段として支持される (原則 2 参照)

### Progressive Disclosure を実装する表現 (タブ / accordion / collapse / 段階遷移)

原則 2 の階層的隠蔽を **手段としてどう実装するか** の例。タブ / accordion はその代表例で、priority hierarchy がある時に secondary を defer する。

#### ふさわしい場面

- 並列カテゴリの情報 (詳細 / Activity ログ / 添付ファイル 等)
- 同時に全部見る必要がない
- ラベルが明確
- primary と secondary を意図的に分離したい

#### ふさわしくない場面

- タブ間で連続的に読まれるべき内容を切り分ける (= 章立て / セクション縦並びが正しい)
- タブラベルが曖昧で何があるか分からない
- タブ間で頻繁に切り替える必要がある (= 切替コストが過大)

### 詳細パネル常時並列 — レビュー型 UI で原則 4 を満たす例

レビュー型 UI (= リスト + 1 件の詳細を行き来する) では、**詳細パネル常時並列** が主タスクの連続性に対して優位な場面が多い:

| 案 | 主タスク (連続編集) の流れ | 他項目との比較 | 親画面情報 |
|---|---|---|---|
| **詳細パネル常時並列 + 全 inline** | リストで次をクリック → 右が切替 → そのまま編集 = **切れ目なし** | ◯ | ◯ |
| Sheet で詳細表示 | 開閉操作が毎回発生 | △ Sheet がリストを部分的に覆う | △ |
| Modal で詳細表示 | Modal 開閉が毎回。親画面遮断 | × | × |

PC 利用前提で画面幅に余裕がある業務 SaaS では、常時並列が優位。Sheet が活きるのは「リスト全幅を見たい時間と詳細を見たい時間が分かれる構成」(= モバイル / 一覧主体の画面)。

ただしこのカタログを機械的に他のプロダクト種別（例: モバイル中心 / コンシューマ向け）へ自動拡張しない。原則（priority hierarchy / 動線重複の排除 / メリハリ）に立ち返って判断する。

## 思考プロセスの順序 (まとめ)

1. **目的関数を 1 行で立てる** (誰が何をする装置で、何を最適化するか) — [SKILL.md](./SKILL.md) Step 1
2. **既存実装を一度忘れる** (ゼロベース / 原則 1)
3. **出力面ごとに読み手を確定する** (宛先分離 / 原則 6) — 画面以外の出力面 (エクスポート等) があるなら、この時点で宛先の違いを設計に織り込む
4. **Priority hierarchy を判定する** (フラット vs 階層化 / 原則 2)
5. **構図を組み立てる** — 上の例示カタログから選ぶか、原則を満たす別表現を採る
6. **動線重複を排除する** (原則 4)
7. **メリハリと S/N を仕上げる** (原則 3) — [SKILL.md](./SKILL.md) Step 3
