# UI Design Skill（事前・構図づくり）

## Purpose

UI 実装の **入口** で、要素を整える前に「この画面は何を最適化する装置なのか」を確定する。

**「大きく作り替える」の閾値**: 新規 feature ディレクトリの作成、または画面の主動線・表現の型を変える変更が該当する。文言修正・スタイル微調整は対象外。

事後レビュー（[ui-review](../ui-review/SKILL.md)）は「各要素が説明できるか」「世界観に合うか」を点検できる。だが **出発点の構図が弱ければ、いくら事後で叩いても直しきれない**。「個別要素は説明可能なのに全体が用を成さない」状態は、事後監査では捕まらない。それを防ぐのがこのスキル。

### なぜ必要か（叩き続けるのを止める）

良い UI が一発で出ない時、原因はたいてい「制約（デザインシステム定義 / primitive / token / 既存構造）の中で、**既存に差分を当てる編集モード**に入り、画面全体の目的関数を持たずに要素を1個ずつ整えている」こと。目的関数がないと、「Tooltip 付けとくか」「丸に少し差をつけるか」と個別最適し、一個ずつは説明できても全体としてユーザーの目的を果たさない。これが「指摘 → 修正」の往復が止まらない構造的な原因。

**対策は事後チェックを増やすことではなく、入口で目的関数を立てること。** このスキルはそこだけを担う。

## 手順

### Step 1 — 目的関数を1行で立てる（最重要）

> **「この画面/コンポーネントは、〈誰〉が〈どの業務〉で使う、〈何〉を最適化する装置か」を1行で書く。**

これを書かずに要素の実装に入らない。例:

- 差分マトリクス = 「担当者が影響範囲を**一覧で高速にスキャン**し、影響が固まっている箇所を掴む装置」→ 最適化対象は **走査の速度と正確さ**
- 課題一覧 = 「担当者が**今日着手すべき課題を選ぶ**装置」→ 最適化対象は **優先度の判断**
- 詳細パネル = 「1件を**深く理解し次アクションを決める**装置」→ 最適化対象は **理解と意思決定**

悪い例:

- ×「ユーザーが情報を見やすく確認する装置」— 誰でも・どの画面でも言える。最適化対象が判断/操作の速度・正確さのどれかまで特定できていない
- ×「既存の一覧画面を改善する装置」— 既存が出発点になっており目的関数ではない

**合格判定**: この1行から「何を強調し何を隠すか」が演繹できなければ書き直し。「既存画面がこうだったから」は目的関数ではない。

### Step 2 — 目的関数から構図を描く

目的関数に照らして、**まず表現の型**を選ぶ（差分を当てる前に、白紙で構図を考える）。

- **表現の選択**: タブ / テーブル / カンバン / 左右カラム / マトリクス / モーダル / 折りたたみ … 採用する型が目的関数に対して他より優位な理由を言えるか。表現は固定列挙ではなく次元の組合せで探索する（表示タイミング=いつ出すか / 空間配置=どこに置くか / 階層関係=何の下に置くか / 情報粒度=どこまで詳細を出すか / 入力モダリティ=どう操作させるか / 時間性=時系列をどう扱うか / 持続性=常設か一時か）。「現状の表現を別の表現に置き換える」選択肢を必ず一度検討する。
- **探索の検証**: 最低 2 つの表現候補を挙げ、採らなかった候補と却下理由を1行ずつ書く（書けなければ探索していない）。却下候補は 1〜3 個で足りる。7 次元は探索の道具であり、出力では判断に効いた次元だけ言及すればよい（全次元の列挙は不要）。
- **情報の重要度 × 利用頻度で配置を分ける**: schema の全 field を一覧に並べない。重要 × 高頻度 → 表に / 低重要 or 低頻度 → 段階開示（折りたたみ・遷移・モーダル・info）に逃がす。
- **メリハリで視線を誘導する**: 太字 / ハイライト / 文字サイズ / 区切り線 / 余白で、目的関数上「最初に見るべきもの」へ視線を導く。全部同じ強度で並べない。

> **情報設計の原則 (ゼロベース・出自タグ / priority hierarchy & Progressive Disclosure / メリハリ & S/N / 動線重複の排除 / 文献引用作法 / 宛先分離) と、その適用例カタログ (Modal / Sheet / Inline / Tab / 詳細パネル常時並列 等)** は [patterns.md](./patterns.md) に固定してある。判断に迷ったら毎回ゼロから議論せず、まずそこを読む。原則は表現パターン非依存。例示カタログは万能ではなく、原則を満たす別表現を採ってよい。

### Step 3 — 引き算で S/N を上げる（引き算 ≠ 無差別な削減）

仕上げに **信号対雑音比（S/N）** を上げる。引き算の本質は「何が信号で何が雑音か」を **目的関数から判定**して S/N を上げること。無差別にミニマルにすることではない。

- **雑音を引く**: 目的を果たすのに寄与しない装飾・冗長ラベル・「念のため」表示・不揃いな器（行高/セル幅のばらつき）・不随意に発火する動き（一覧スキャン中に逐一開くホバー詳細）。
- **信号を立てる（足すこともある）**: 意味のある差分はむしろ誇張する。例: 一覧の「有/無」を一目で弁別させたいなら、●と・の大小差は小さくせず大きく取る（前注意的処理に乗る）。順序のある程度差は図形量に素直にマップする。
- 「情報を足す」方向に偏らない。提案が「これも表示しよう」ばかりなら、削る方向 / 別表現への置換を必ず一度検討する。

悪い例:

- ×「とにかく要素を減らしてミニマルにした」— 信号まで削っている
- ×「Tooltip で全部補足した」— 隠すべき雑音を足している

> ただし表現が単調になりすぎるのも良くない。リッチにしたことで想定以上の価値が出る場面はある。判断基準は常に **目的関数に対して S/N が上がるか** であって、ミニマルさ自体ではない。弁別が業務判断に効く差分がある場合のみリッチ化を検討し、それ以外は削る方向をデフォルトにする。

## 出力形式

```
## UI Design — <画面名 / コンポーネント名>

### 目的関数（1行）
〈誰〉が〈業務〉で使う、〈何〉を最適化する装置

### 構図
- 採用する表現の型 と その優位性（目的関数に照らして）
- 検討した他候補と却下理由（最低1つ）
- 重要度 × 利用頻度の配置（表に出す / 段階開示に逃がす）
- 視線誘導（何を最初に見せ、何を弱めるか）

### 引き算（S/N）
- 引く雑音: …
- 立てる信号: …

### 原則チェック
- ゼロベース: 既存を根拠にしていないか
- 動線重複: 同じ目的の入口が複数ないか
- 宛先分離: 画面以外の出力面が絡む場合のみ
```

## やってはいけないこと

- 目的関数を立てずに要素を1個ずつ整え始める（＝差分編集モード。叩き続ける原因）
- 「既存画面がこうだったから」を構図の根拠にする（既存が最適とは限らない）
- 引き算を「無差別にミニマルにすること」と取り違える（S/N を上げるのが目的。信号は足すこともある）
- 表現の型を検討せず、最初に思いついた表現に差分を当てる
