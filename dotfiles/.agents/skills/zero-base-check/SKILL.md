# Zero-Base Check Skill（増改築検出 — 構造の全体最適監査）

## Purpose

修正や実装は放っておくと **現状の構造に合わせた増改築** に流れる。既存の分岐パターンに 1 枚足す、既存の回避オプションに乗る、既存の迂回路を延長する — 局所的にはどれも「動く最小変更」だが、歪んだ土台の上に階を重ねる行為であり、次の変更で同じ分岐がまた増える。

本スキルは対象（差分 / 計画 / 領域）を **「今日ゼロから設計したらこの形になるか」** と比較し、症状の層ではなく根本の層を直すべき箇所を検出する。後方互換性より一貫した設計を優先する方針のプロジェクトでは、「既存がこうだから」は増改築を正当化しない。

**ゴールは指摘と根拠の列挙まで。** 修正はこのスキルの責務外。修正に進む場合は通常フロー（issue 化 or その場の実装判断）を別途回す。

## 実例（増改築が起きるパターン）

ある認証機構の実装で、サーバー側は正規の抽象化（複数のバックエンド実装を切り替え可能にする Gateway パターン、呼び出し側に分岐なし）だったが、クライアント側にはテスト用の実装がプロバイダとして存在せず、その欠落を埋めるために

- 本物の設定形状を模した偽の config（「呼び出し元が使わない前提」のコメント付き）
- SDK 初期化を避けるための `enabled: false` オプション
- テスト用の迂回路（専用 Server Action）
- 画面ごとの条件分岐 10 箇所以上

が積み重なっていた。この状態で新画面に別の認証手段を足す際、`googleSignInEnabled` のような prop という **5 枚目のパッチ** を重ねてしまいそうになった。正解はテスト用プロバイダをクライアント側の正規実装として新設し、迂回路を全部消すことだった（実施すれば正味数十行減）。パッチは 1 枚ごとに小さく合理的に見えるが、根本（プロバイダ実装の欠落）を直せば全部不要だった。

## 増改築のシグナル（検出のレンズ)

対象にこれらが現れたら、根本の層がずれている可能性を疑い、ゼロベース導出と比較する。

1. **分岐の増殖** — 同じ条件（環境・モード・プロバイダ・顧客種別）による if / prop が複数ファイル・複数画面に散らばる。またはこの変更がその分岐をさらに 1 箇所増やす。正しい層に抽象（実装の差し替え点）があれば分岐は 1 箇所に集約されるはず
2. **回避オプション** — `enabled: false`・`skipXxx`・`disableYyy` のような「本来の動作を止めるための引数」。何かを避けるためのオプションは、避けたい対象の設計が呼び出し側の都合に合っていない兆候
3. **嘘のデータ / ダミーの通過** — 「実際には使われない前提」の値・「型を満たすためだけ」の実装・呼び出し元が握りつぶす前提の戻り値。契約と実態がズレている
4. **迂回路** — 正規フローと並走する専用ルート（専用 action・専用 endpoint・専用 util）。正規フローがその入力を受け入れられない理由を問う。受け入れられるように正規フロー側を直す方が全体最適であることが多い
5. **非対称** — 対になるべきサブシステム（client / server、SaaS / セルフホスト、feature A / B）の片方だけに抽象があり、もう片方は分岐でしのいでいる
6. **プロップドリリング化した特殊事情** — 1 つの事情（例: テスト環境である）を伝えるためだけの prop / 引数が層を貫通している。事情の発生源に近い層で解決できないか
7. **後方互換の亡霊** — 旧実装への配慮・新旧並走・「壊さないため」のラッパー。後方互換を明示指示なく重視しない方針のプロジェクトでは、削除できるものは削除する PR を同梱する
8. **同型コードの N 回目** — この変更が既存の類似コードの複製 + 微修正なら、N 個目を作る前に共通の土台へ持ち上げるべきかを問う（ただし温度感に注意 — 下記）

## 手順

1. **対象と変更目的を 1 行で確定** — `〈何を達成するため〉に〈どこ〉を変える（変えた）`。引数で差分（PR / ブランチ / working tree）か計画かを特定。指定がなければ `git diff` の現在差分を対象とする
2. **現状構造の把握** — 対象が触る領域の構造（層・抽象・分岐・対称物）を読む。**対象の diff だけでなく、その周辺の「合わせにいった相手」を必ず読む**。増改築は diff の中ではなく、diff が従った既存構造の中にある
3. **ゼロベース導出** — 既存実装を見なかったことにして「この目的を今日ゼロから設計したらどういう形か」を 3-5 行で書き出す。このとき後方互換・既存の流儀への配慮は入れない
4. **比較と出自タグ付け** — 実際の変更（or 計画）とゼロベース形の差分を列挙し、各差分に出自を付ける: **目的由来**（要件がそうさせた）/ **相続**（既存構造がそうさせた）。相続タグが付いた差分が増改築候補
5. **シグナルとの突合** — 上記 8 シグナルで対象と周辺を走査し、候補を追加する
6. **修正の層を提案して終了** — 各指摘に「症状の層での対症」と「根本の層での修正」を併記し、根本修正のおおよその規模（触るファイル数・波及範囲）と確信度（%）を添える。確信度は 90 以上=構造から断定できる、70=設計意図の推測に依存、50=推測が主。50 未満は書かない。修正はしない。検出ゼロなら「増改築なし」と明言する

## 温度感（過剰検出の抑制）

小規模チームや検証段階のプロダクトでは、ゼロベース比較は **抽象の先取りを推奨するものではない**。以下は指摘しない:

- まだ 2 回しか現れていない重複の共通化（3 回目が見えてから）
- 将来の拡張に備えたインタフェース・汎用化の先取り
- 動いている既存構造のうち、今回の変更が触れも依存もしていない部分の作り直し提案（それは別 issue の話。今回の変更が **その構造に合わせて歪んだ場合のみ** 指摘する）
- イベントソーシング・CQRS 等の重い基盤への持ち上げ

判断基準は「この増改築を許すと **次の変更でまた同じパッチが増えるか**」。増えるなら根本を指摘し、今回限りで閉じるなら対症で良い。プロジェクトのチーム規模・検証段階に関する前提（CLAUDE.md 等）があれば、それに沿って温度感を調整する。

## 出力形式

```md
## Zero-Base Check — <対象>

### 変更目的
- 〈何を達成するため〉に〈どこ〉を変える

### ゼロベース形
- （既存を見なかった場合の設計を 3-5 行）

### 結論
- 増改築なし / 増改築 N 件（うち根本修正を推奨 M 件）

### 指摘（優先度の高いものから）

#### 1. <箇所>（確信度: NN%）
- シグナル: 分岐の増殖 / 回避オプション / 嘘のデータ / 迂回路 / 非対称 / プロップドリリング / 後方互換の亡霊 / 同型 N 回目
- 現状の形: <どういうパッチになっているか。従った既存構造も明記>
- 根本の層: <どこを直せば構造ごと解消するか>
- 対症で許容する場合の条件: <今回限りで閉じる根拠があるなら。なければ「なし」>
- 根本修正の規模: <ファイル数・波及・テスト影響の目安>

### 出自の棚卸し
- 目的由来: <要素 → 理由>
- 相続: <要素 → 従った既存構造>
```

### 良い指摘 / 悪い指摘の対比例

- 良い例: 「`googleSignInEnabled` prop: テスト環境の事情を上位コンポーネントからフォームに伝えるためだけの貫通 prop で、既存の `enabled` オプション（それ自体が偽 config の回避策）に従った相続。根本はクライアント側にテスト用プロバイダ実装が無いことで、専用プロバイダを足せば prop・オプション・専用 action が全て消える（確信度 90%、影響範囲 14 ファイル）」
- 悪い例: 「認証周りは複雑なのでリアーキテクチャすべき」（層の特定・出自・規模がない）

## やってはいけないこと

- **修正まで進める** — ゴールは列挙まで。パッチ・コード変更を出力しない
- 指摘ゼロを恐れて弱い指摘を捻り出す（「増改築なし」は正当な結論）
- ゼロベース形を書かずに現状との差分を語る（比較対象がなければ増改築は定義できない）
- 「既存がこうなっているから」を指摘の反証として受け入れる（既存構造は正しさの根拠にならない。正しさは目的からの導出で示す)
- 温度感を超えた理想論（先取り抽象・重い基盤）を根本修正として提案する
- 対象の diff の中だけを見る（増改築は diff が従った周辺構造との関係の中にある）
- 根本修正の規模を添えずに「こっちの方が綺麗」とだけ言う（採否はユーザーの判断であり、判断材料は規模と波及）
