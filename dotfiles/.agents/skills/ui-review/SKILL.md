# UI Review Skill（事後・点検）

## Purpose

UI / frontend 変更を以下の 4 軸で点検する。ファイル diff だけのレビューでは画面シェル違反・独自実装の混入・認知過多・各状態の挙動破綻が見えないため、それを補う。

1. **プロダクトのデザインシステム定義（例: DESIGN.md 等）に従っているか**
2. **デザインシステム primitive（+ 必要最小限のカスタムスタイル）で組まれているか**（独自実装は基本禁止）
3. **[ui-design](../ui-design/SKILL.md) 観点で、その UI 表現が「今この場面で本当に最適か」**（目的関数に対して S/N が上がっているか）
4. **コード演繹で、各要素・各状態の挙動が破綻なく説明できるか**（primitive のソースまで展開し、hover / focus / selected / responsive / コンテンツ状態を机上で確定）

> このスキルは **事後の点検**。実装の入口（構図づくり）は [ui-design](../ui-design/SKILL.md) の責務。「個別要素は説明可能なのに全体が用を成さない」を捕まえるには、出発点で目的関数を立てる ui-design が要る。事後レビューだけで叩き続けない。

## 発動条件

以下のいずれかに該当したら必ず起動する。

- フロントエンドの page / feature / component 相当のディレクトリの変更
- デザインシステム定義ドキュメントの改定 / スタイル設定（Tailwind config 等）の変更 / primitive の追加
- 「UI 確認して」「画面どう見える？」「レビュー」「UI をコードでチェック」「ホバー / 状態の挙動を確認」と依頼があり、対象が UI を含む

実装完了の宣言前に必ず通す。typecheck / test green は「各状態でどう振る舞うか」を何も保証しない。

## You Must Read

- 変更したコンポーネント本体
- **そのコンポーネントが使う全 primitive / 共通コンポーネントのソース**（例: `<frontend-src>/components/ui/*.tsx`）。
  これを開かずに「自分が書いた className」だけで判断するのが、軸 4 の見落としの最大の原因。primitive が base / variant で当てている class を必ず展開する。
- `cn()` / `cva()` 等でマージされる全引数（条件付き class、variant、デフォルト）
- そのコンポーネントを render する **画面シェル**（アプリ全体のナビゲーション・レイアウトを定義するルート layout や、ワークスペース単位の中間 layout）
- プロダクトのデザインシステム定義ドキュメント — 装飾・見た目の絶対回避事項の正本（あれば参照）
- トークンの実値（spacing / radius / color の意味）はデザインシステム定義ドキュメントには無いことが多い。グローバル CSS のトークン定義ファイルと primitive 実体から演繹する
- [ui-design/SKILL.md](../ui-design/SKILL.md) — 構図・S/N の正本

## レビュー観点

### 軸 1: デザインシステム定義への準拠（lint で取れない領域に集中）

> 機械で確定できる項目（raw HTML 要素 → primitive 強制、固定色直書き禁止、指定外アイコンライブラリの import 禁止、内部リンクの `<a>` タグ直書き禁止 等）は、プロジェクトの lint ルールが備わっていれば全件捕捉される。lint が担保している範囲は skill では再チェック不要。
>
> skill が見るのは **「lint が原理的に取れない世界観・設計判断」** のみ。

- タイポグラフィ: 定義されたフォントセット（欧文 / 和文 / フォールバック）が揃っているか
- スペーシング / ボーダーラジウス: グローバル CSS のトークン定義から外れた値・任意の px 直書きをしていないか（数値をここに固定で書かない。実コードから毎回演繹する — ドリフトするため）
- カラートークン: `bg-card` / `text-foreground` / `border-border` 等の semantic token を使っているか。token の **意味** を誤用していないか（`status-success` を未完了の対象に使う等）
- 画面シェル（アプリ全体の外枠を組むレイアウトコンポーネント）が崩れていないか
- 画面語彙: 内部 domain 用語（DB エンティティ名やコード上の型名）をそのまま UI に出していないか。業務語彙に置き換わっているか

### 軸 2: デザインシステム primitive 強制（独自実装は基本禁止）

UI コンポーネントは **デザインシステム primitive（必要に応じて className でカスタムスタイル）** で組むのが原則。独自の `MyButton` / `MyCard` 等を作って primitive を迂回するのは禁止。

- 独自再発明コンポーネント（`MyButton` / `MyCard` / `CustomDialog` 等）を作って primitive を迂回していないか
- primitive **の選び方** が用途に合っているか（単一値選択で `DropdownMenu`、トグルで `Checkbox`、確認で `Dialog` のような誤用がないか）
- primitive を使っているが **className 上書きで世界観を破壊** していないか（例: `<Button className="bg-card text-foreground border-none">` のような解体）
- カスタムスタイルは「必要最小限」か。primitive のバリアント追加で済むものを独自実装に逃げていないか

### 軸 3: ui-design 観点（その表現が「今この場面で本当に最適か」）

原則・判断基準は [ui-design/patterns.md](../ui-design/patterns.md)（ゼロベース思考 / priority hierarchy & Progressive Disclosure / メリハリ・S/N / 動線重複排除 / 宛先分離）が正本。ここでは事後点検として以下を確認する。

- **目的関数**（〈誰〉が〈業務〉で使う、〈何〉を最適化する装置か）が成立しているか
- 採用表現・情報の配置（重要度 × 利用頻度）・メリハリが、目的関数と patterns.md の原則から演繹して説明できるか。「既存画面がこうだったから」は理由にならない
- 各要素の**出自**を問えるか: 「目的から導出」か「成果物から相続」（過去実装・データ構造・テンプレの名残）か。相続しか根拠が出ない要素は存在意義を再導出できなければ削除候補（patterns.md 原則 1）
- 変更に画面以外の出力面（エクスポート・通知）が絡むなら、宛先分離（patterns.md 原則 6）を軸 1 の画面語彙チェックと併せて確認する

### 軸 4: コード演繹（各要素・各状態の挙動の正否）

React + ユーティリティ CSS + デザインシステム primitive は決定論的なので、各状態の描画は **コードから 100% 演繹できる**。実機操作で hover / scroll を1つずつ試すのではなく、**演繹で確定する**。

**手順:**

1. **適用 class を完全合成する** — 要素ごとに `primitive の base + variant + cn() に渡した自前 className + 条件付き class（isSelected && '...'）` を合成し、DOM に当たる class の集合を確定する。**primitive のデフォルトが効いていることを見落とさない**（例: デザインシステムのテーブル行コンポーネントは className を渡さなくても `hover:bg-secondary` が付く → ヘッダ行で列見出しが全部光る）。
2. **状態マトリクスで演繹する** — 各要素に最低この状態を当てる:
   - **base** / **`:hover`**（自要素 / `group-hover` / 親 hover が **どの DOM 範囲に波及するか** を特定）/ **`:focus-visible`** / **`:active` / `:disabled`**
   - **選択状態**（`data-[state=selected]` / `aria-current` / 自前 `isSelected`。表現軸が何重か。1 軸で足りるのに border + ring + bg を重ねていないか）
   - **レスポンシブ**（`sm: md: lg:` で消える / 壊れる / 重なる箇所）
   - **コンテンツ状態**（空 / 1 件 / 多数 / 長文の折返し・`line-clamp`・`truncate` / `null` / 数値 0）
3. **3 つの問いを当てる** — ① 意味があるか（説明できる目的があるか。なければ削る。例: 列見出し hover で全列点灯 = 意味なし）② 一貫しているか（行 / 列、カード同士、ボタン同士で挙動・表現軸が揃っているか）③ 破綻がないか（下記の構造系）。

**構造系チェック（決定論的に追える）:** `sticky` / `overflow` / `z-index` / `position` / `border-collapse` / `table-layout` / 角丸 + `overflow-hidden` の組合せが、スクロール・固定・重なり・サブピクセルで破綻しないか（例: `border` 付きセルの `border-collapse` + `sticky` ヘッダで境界線が消える/二重になる、`rounded-*` + `overflow-hidden` の親子で角の 1px 隙間。コード演繹で確定しきれない場合は大局スクショ確認に回す）。スクロールコンテナの祖先が二重化していないか。

> **絶対基準: 全要素・全状態について「なぜそうなっているか」を合理的に説明できなければ不合格。** 「機能的に壊れていない」では合格にしない。説明できない挙動は事故 / 惰性 / primitive デフォルトの漏れ。意味がないなら削る。主観的な美的好みは別枠（提案）に分離し、合否判定と混ぜない。
>
> 対象は diff で変更した要素と、その変更が挙動・見た目に影響を与える既存要素まで。diff と無関係な既存要素は対象外。繰り返し要素（テーブル行等）は同一 map から生成される限り 1 種として演繹し、状態の異なる代表（選択行・空値行・長文行）だけ個別に当てる。

ダッシュボード系画面では「**何を別画面に逃がすか / 何を 3 秒で伝えるか**」が主軸。

## 実機の位置づけ（限定的）

- **インタラクションの正否（hover / scroll / click / 選択 / レスポンシブ）は実機に頼らない。** 軸 4 のコード演繹で確定する。実機でホバーやスクロールを1つずつ手で試して挙動を確かめる運用は採らない（網羅できず、決定論的に分かることを観測で代替するのは本末転倒）。
- 実機は **最後に 1 画面スクショで「大局」だけ** 見る用途に限る: 余白・密度・色バランス・全体の見栄え。ここは演繹より知覚が速い領域。

```sh
<開発サーバ起動コマンド>
# → 対象 URL（実 URL はルーティング定義から演繹する）
# 大局を1枚
```

スクショが撮れなかったら **「コード演繹は完了、大局スクショ未確認」と明示** する。「OK」と単独で言わない。

## 独立性（サブエージェントで回す場合）

この節はレビューを別エージェントに委譲する場合の指示。自己完結で実行する場合は適用外（ただし「自分の diff だけで判断せず primitive のソースまで辿る」原則は同じ）。

軸 4 を別エージェントに任せる時は、**実装者の想定（どう実装したか / どこを見てほしいか）を渡さない**。実装者の指示の範囲で動くと実装者の盲点がそのまま伝染する。「指示の範囲はカバーの下限であって上限ではない。実装者が見落としている前提で、primitive のソースまで辿って独立に演繹し直せ」と指示する。

## プロジェクト固有の追加レビューについて

このスキルは **4 軸チェックのみ** を担当する。プロジェクト固有の追加 UI レビュー（専用 subagent や別ワークフローがあれば）は呼び出し元の責務とし、このスキル内では起動しない。

## 出力形式

```
## UI Review — <画面名 / issue #NNN>

### Critical / High
- [severity] area: ...

### 軸 1: デザインシステム定義への準拠 / 画面語彙
- ...

### 軸 2: primitive 強制 / 独自実装の混入
- ...

### 軸 3: ui-design 観点（目的関数に対して S/N が上がっているか）
- 「<ユーザー像>が<業務>で<悩み>を抱えながらこの画面を使う」が成立しているか
- 雑音を引いたか / 信号を立てたか / 別表現への置き換えを検討したか

### 軸 4: コード演繹（各要素 × 各状態）
- <要素>: base=… / hover=…（波及範囲）/ selected=…（表現軸の数）/ responsive=… / 空・長文=…
  → 各状態の合理的理由。説明できない挙動があれば不合格として列挙

### 大局確認（実機スクショ）
- 余白 / 密度 / 色バランス: …（撮れなければ「コード演繹のみ、大局未確認」と明示）

### 推奨
approve / changes-requested / block
- デザインシステム定義の絶対回避リスト違反・primitive 再実装・内部 domain 用語の画面露出が 1 件でもあれば block
- 軸 4 で説明できない挙動が残っていれば block 寄り
- 惰性要素・一貫性欠如のみなら changes-requested
- 指摘が提案のみなら approve
```

## やってはいけないこと

- typecheck / test green だけで「OK」と報告する
- 自分が書いた `className` だけで判断し、**primitive のソースを開かずに**「hover 効果なし」等と断定する
- 演繹を「自分が書いた diff」で打ち切る（最終的に当たる class の集合・全状態まで展開しない）
- インタラクションの正否を実機操作の観測に依存させる
- 説明できない挙動を「機能的に害がないから」と合格にする
- 主観的な好みを合否判定に混ぜる（提案として分離する）
- 「情報を足す」方向に偏った提案を主軸にする（削る方向 / 別表現への置き換えを必ず一度検討する）
- 内部 domain 用語をそのまま画面に出す変更を見逃す
- **lint で機械的に取れる項目（raw HTML 要素・固定色・指定外アイコンライブラリ等）を skill レベルでチェックし直して時間を浪費する**
- 「既存画面がこうだったから」を採用理由として通す

## 動線・状態系の観点

低頻度操作の主動線化、空状態/disabled/破壊的操作の次アクション欠如、多重モーダル・多重スクロールなど利用シーン・動線に起因するアンチパターンは [ui-check](../ui-check/SKILL.md)（見た目・利用シーン統合監査）の責務。このスキルの軸 1〜4 と合わせて必要なら ui-check も通す。
