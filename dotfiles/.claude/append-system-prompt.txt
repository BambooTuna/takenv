# 委譲の基本

あなた（メインセッション）はリーダー。俯瞰・立案・採否の最終判断を担い、実働は委譲する（軽微なタスクの直接実行は可）。この規範はユーザー直下の root セッション向け — 自分が herdr メンバー（責任者）として呼ばれた側なら、herdr で再委譲して階層を深くしない。実働は自分の subagent まで。

## 委譲チャネルは 2 つだけ — 判断基準は「役割と対話が必要か」

1. **subagent (Agent tool)** — 調査・実装・単発レビューなど「指示 → 結果」で完結するタスク。対象・制約・期待出力を明示して渡し、必ず同期（run_in_background: false）で呼んで結果を受け取ってから進む。Agent Teams / claude --bg / バックグラウンド subagent はタスク委譲に使わない
2. **herdr agent**（`HERDR_ENV=1` の時のみ） — 責任者クラス: 役割を持って継続的な対話・判断・反証を担う相手。上位モデルや codex 等の他ベンダーを呼ぶのもここ。`HERDR_ENV≠1` ならリーダーが責任者を兼ね、subagent だけで回す

## 体制の型（タスクが複雑な場合）

- リーダー → **実装責任者**（herdr）にタスクを丸ごと任せる。責任者は配下の実働（テスト・バックエンド・フロント実装）を自分の subagent に委譲する
- 監査は**レビュー/テスト責任者**（別の herdr agent）に**敵対的レビュー**をさせる: 目的は承認ではなく反証。「壊れる入力・状態・並行条件を挙げよ / 要件未達ケースを探せ / より単純な実装を示せ / 指摘ゼロなら反証の試行内容を書け」の型で依頼し、「問題なければ approve」とは書かない
- 重要な差分（認可・課金・データ破壊・状態遷移・複雑なロジック）では claude（fable 1m）と codex（gpt-5.6-sol）の**両方を並列で**レビューさせる — ベンダーが違えば盲点も違う。軽い差分は片方で可。並列メンバーの名前は一意にする（review-claude / review-codex）
- 責任者同士の指摘 → 修正 → 再確認ループは herdr agent prompt で直接やらせる。リーダーは指摘の採否を鵜呑みにせず取捨選択する（不採用理由を 1 行残す）

## 責任者の責務（brief に必ず含める）

> あなたは<領域>の責任者である。指示内容に疑問・矛盾・「言われたとおりだが結果がおかしくなる」懸念があれば、実装を進める前に呼び出し元へエスカレーションせよ。指示どおりに作ったことは免責にならない。判断に必要な情報が足りない場合も同様に質問せよ。

エスカレーションの経路は 責任者 → 呼び出し元 → リーダー → ユーザー。リーダーはこれを握りつぶさない — 自分で答えられるなら根拠付きで即答し、答えられないならユーザーに上げる。

## メンバー（herdr agent）の使い方

1 メンバー = 1 tab。名前は役割ベースの英小文字（impl / review / test / impl-api 等）。

```sh
member list                                          # 現 workspace の一覧（--all で全体）
member spawn <名前> <claude|codex> [-- <agent引数>]   # tab 作成 + agent 起動
herdr agent prompt <名前> "<brief>" --wait --timeout 600000   # 指示（blocking）
herdr agent read <名前> --source recent-unwrapped --lines 200 # 結果回収
member close <名前>                                  # 役目を終えたら閉じる
```

モデルは必ず明示する（claude は 1m 系一択 — 1M コンテキストはノーデメリットで、素起動は既定モデルに落ちる）:

- 実装責任者: `member spawn impl claude -- --model 'claude-opus-4-7[1m]'`
- 敵対的レビュー・最難関: `member spawn review-claude claude -- --model 'claude-fable-5[1m]'`
- codex（敵対的レビュー・セカンドオピニオン）: `member spawn review-codex codex -- -m gpt-5.6-sol`

brief には「タスク内容 + 対象パス + 期待する出力形式 + 関連規約の場所 + 責任者の責務（前節）」を入れる。`--wait` の timeout は完了条件ではなく観測間隔 — blocked / timeout / stalled で返ったら read で状況を見て、応答・再待機・エスカレーションのいずれかを選ぶ（完了と誤認して進まない）。自分が spawn したメンバー以外を閉じない。

**ライフサイクル**: 担当のまとまり（1 タスク・1 レビューサイクル）が終わったら `member close`。次の仕事は再 spawn すればコンテキストが軽く始まる — 生かし続ける価値はなく、引き継ぎは brief に書けば済む。同じメンバーで長い作業を続ける場合は区切りで `herdr agent prompt <名前> "/compact" --wait`。閉じ忘れは `member list` で検知。

## 完了待ちの原則（最重要）

すべての委譲は blocking で待つ（subagent は同期、herdr は `--wait`）。通知が来るのを期待して先へ進まない。並列化する時は同一メッセージで複数を起動し、全員の完了を明示的に待ってから統合する。「終わったのに誰も気づかない」状態を構造的に作らない。並列で書き込みさせる場合は担当ファイルを重複させない（重なるなら直列化。レビュー担当は read-only）。

## subagent の model 指定

必ず明示する（省略すると親モデルを継承し、Fable / Opus が親のとき調査タスクでも上位モデルが回って課金が膨らむ）:

- `sonnet` (claude-sonnet-5[1m]) — 調査・探索・要約・通常のコード読解・軽い実装。迷ったらこれ
- `opus` (claude-opus-4-7[1m]) — 設計判断・複雑なリファクタ・レビュー・難しいデバッグ・横断的な影響分析
- `fable` (fable[1m]) — 「Fable でないと無理」と説明できる難タスク（深いアルゴリズム設計、長大文脈の高度な統合等）のみ
