# x-draft-batch — X 投稿下書きバッチ作成スキル

CTO 個人アカウントの**採用導線**運用を前提に、週1-2回のペースで投稿下書きを一気通貫バッチ生成する。

## 前提と依存

- **ペルソナ・運用方針**: `~/.claude/skills/x-ops/persona/` に定義済み（`profile.md` / `tone.md` / `goals.md` / `tweet-samples.md` / `watchlist.md`）
- **Claude Code ログ集約**: `worklog-digest` スキルに委譲
- **X API 操作**: `xurl` スキル経由（高コストなので1回で取り切り、結果JSON保存して再利用）
- **投稿は絶対に自動実行しない**。親は下書きを提示しユーザー承認を待つのみ

## 起動条件

以下のいずれかで発火：

- 「Xの下書き作って」「X投稿考えて」「今週のXネタ」「X週次バッチ」等のバッチ系依頼
- 明示的な `/x-draft-batch` 的呼び出し
- 単発の「このツイートに返信」等は対象外（`x-ops` 単独で処理）

---

## 実行パラメータ（ユーザー指定で上書き可）

起動時、ユーザー指示から以下を抽出する。**明示指定があればデフォルトを必ず上書き**すること。

| パラメータ | デフォルト | ユーザー指定の例 |
|---|---|---|
| 期間 | 過去7日 | 「過去3日」「今日」「今週」等 → 明示指定を優先 |
| 下書き本数 | 3-5本 | 「1本だけ」「3本」「2本」等 → 明示指定を優先 |
| X API 使用 | 使う（Step 1-C 実行） | 「軽く」「ざっくり」「X API不要」「--no-x」→ Step 1-C skip |
| 情報源 skip | なし | 「Slack使わないで」「Claudeログ無視」等 → 該当 Step skip、欠損は最終出力で明示 |

### 本数が1本の場合の縮退ルール
- Step 2 のコンテンツ比率（実況40/所感30/カルチャー20/学び10）は1本では満たせない → 「次回以降で調整」と計画内に言及するのみ
- Step 3 は1エージェント（または inline 1回）で3案生成
- 最終出力フォーマットは「投稿1」ブロック1つで成立する

### 「軽く」「ざっくり」指示のスコープ
- Step 1-C（X API）を skip するのみ。Step 1-A/B と Step 2/3 は通常通り
- 追加で Step 1-A/B も skip したい場合はユーザーが明示指定する必要あり（勝手な拡大解釈はしない）

## 実行モード（ネスト dispatch 不可時のフォールバック）

本スキルは **サブエージェント並列起動** を前提とするが、親セッションが subagent として動作中、Task tool が無効化されている等で**ネスト dispatch 不可** の環境では、以下のフォールバックを取る。

### モード判定（スキル起動直後に必ず実施）
1. Task tool（Agent dispatch）が使用可能か確認
2. **可能** → 並列モード（SKILL全文通り、Step 1 を 3 subagent 並列・Step 3 を本数分並列）
3. **不可** → 直列 inline モード（親が各 Step のプロンプト内容を順次実行）

### 直列 inline モードの動作
- Step 1 の 3エージェント分のプロンプト内容を、親が**順次 inline で実行**する
  - 実行順は Step 1-A（Claudeログ）→ Step 1-B（Slack）→ Step 1-C（X API） の順
  - X API は高コストなので最後、かつ失敗時は他素材で続行
  - 各ステップの出力を中間成果物として会話に保持
- Step 2 も親が inline 実行（ペルソナ読込 → 計画策定）
- Step 3 も親が投稿本数分 inline で実行（各投稿3案）
- 最終出力サマリに **「実行モード: 直列 inline（ネスト dispatch 不可）」** を明記

### 並列/inline どちらでも共通の絶対ルール
- 実行パラメータ（期間・本数・skip指定）の解釈は同一
- ユーザー承認前の自動投稿禁止
- 情報源欠損時は最終出力で明示

---

## 全体フロー（3ステップ・並列モード時は全ステップでサブエージェント使用）

```
[Step 1: 情報収集]  → 3つのサブエージェントを並列起動
       ↓
[Step 2: 投稿計画]  → 1つのサブエージェントに計画策定を委譲
       ↓
[Step 3: 下書き作成] → 投稿本数分のサブエージェントを並列起動
       ↓
[最終提示]          → 親が統合してユーザーに提示、承認を待つ
```

**サブエージェント委譲の理由**:
- 親のコンテキストウィンドウを情報収集の生データで汚さない
- 並列化で所要時間を短縮
- 各ステップの責務を明確に分離（情報 / 戦略 / 執筆）

## Step 1: 情報収集（3つのサブエージェントを並列起動）

Agent ツールで `general-purpose` を**3つ同時に**起動する。**1つのメッセージに3つの tool use を含めて並列実行すること**。

### Agent A: Claude Codeログ収集

```
description: "Claude Codeログから投稿ネタ抽出"
subagent_type: "general-purpose"
prompt: |
  あなたはX投稿ネタ探しのリサーチャーです。以下を実行してください。

  ## タスク
  `worklog-digest` スキル（~/.claude/skills/worklog-digest/SKILL.md）の手順に従い、
  過去7日（ユーザーが別期間を指定していればそれ）の全プロジェクト横断の作業ログを集約してください。

  ## 出力要件
  下記4分類で、X投稿の素材として使える粒度のエピソードを各分類10件まで抽出：
  - **学び・気付き**: 具体的に何を試して何が分かったか
  - **詰まりポイント**: 症状→原因→解決の3点セット
  - **意外だったこと**: 想定と違った挙動・発見
  - **技術的意思決定**: 何を採用/却下し、なぜか

  ## 厳守事項
  - 機密情報（社内固有名詞・APIキー・顧客名・個人名・未公開調達情報）は必ずマスク
  - 抽象的な要約ではなく具体エピソードと引用を優先
  - 「今日は○○をやった」系の日常作業は省く

  ## 出力フォーマット
  Markdown。各エピソードに元プロジェクト名・日付・簡単な文脈を付ける。
```

```
description: "X情報収集（ブックマーク/いいね/トレンド）"
subagent_type: "general-purpose"
prompt: |

  1. 自分のブックマーク直近20件
  2. 自分のいいね直近20件

  ## コスト制約（厳守・破産防止）
  ### 呼び出し前の必須チェック
  1. **先に当日ファイルを確認**: `ls /tmp/x-draft-batch-*-$(date +%Y%m%d)*.json 2>/dev/null`

  - 「もう一度検索すれば取れるかも」の発想は破産入口。やらない
  - 再検索はしない。取り損ねは諦めて次に進む

  ## 出力フォーマット（3軸で要約）
  - **参考にしたいスタイル**: ブックマーク/いいねから見える「良いと感じた文体・構成」3-5例
  - **反応したい話題**: 業界で今話されている、自分のペルソナで絡める余地のあるトピック3-5件
  - **業界の今のテンション**: ターゲット層（エンジニア・スタートアップ）の温度感を1段落

  watchlist.md が空なら「情報源未定義」と報告してスキップ。
```

## コスト管理（xurl 呼び出しの厳格ルール）

X API は高コスト。**パースエラーや再試行での重複呼び出しは破産リスク** なので以下を絶対遵守。

### 呼び出しの 5 原則（Step 1-C とその他すべての xurl 呼び出しに適用）

1. **呼び出し前に当日ファイルを必ず確認**
   `ls /tmp/x-draft-batch-*-$(date +%Y%m%d)*.json 2>/dev/null` を先に実行。
   **当日分が存在すれば Read で再利用し、新規 xurl 呼び出しは禁止**。

2. **1 バッチ 1 回で取り切り**
   複数エンドポイントを欲張らない。`-n` で件数を最小化。

3. **取得直後に必ず生JSONをファイル保存**
   保存前に要約・パース処理に進まない。
   ファイル名: `/tmp/x-draft-batch-<endpoint>-<YYYYMMDD-HHMMSS>.json`
   （例: `x-draft-batch-bookmarks-20260420-143012.json`）

4. **パースエラー時は再呼び出し禁止**
   保存済みJSONから**再パースのみ**で対処。JSONが不完全な場合も **その回は諦めて** Step 1-C を「取得失敗」として続行。
   「もう一度検索すれば取れるかも」の発想は破産への入口。絶対にやらない。

5. **再検索禁止**
   一度取得したデータで不足しても、その回のバッチでは追加取得しない。不足は次回に回す。

### Step 1-C の subagent プロンプトに必ず含めるルール（運用徹底）

本 SKILL.md の Step 1-C テンプレートには以下を必須で含めること：
- 「呼び出し前に `ls /tmp/x-draft-batch-*-$(date +%Y%m%d)*.json` で当日ファイルを確認」
- 「当日分があれば Read で再利用、新規 xurl 呼び出し禁止」
- 「新規取得時は即座に `/tmp/x-draft-batch-<endpoint>-<timestamp>.json` に保存してから要約」
- 「パースエラー時は再呼び出し禁止、保存済みJSONの再パースのみ」

### その他コスト管理

- サブエージェント起動は合計 3 + 1 + N（投稿数）= 7-9個程度
- ユーザーが「軽く」「ざっくり」等を明示した場合は Step 1-C をスキップ可
- `--no-x` オプション相当の指示があれば Step 1-C なしで進行

## 失敗時・欠損時の対応

### 情報源欠損（ユーザーからの skip 指示 or エージェント失敗）
1. 親は **他の系統で続行**（3系統すべて欠損時のみ停止）
2. 最終出力サマリに **欠損を明示**（例: 「Slack: ユーザー指示により skip」「X: API エラーで取得不可」）
3. 欠損が計画品質に響く場合、投稿本数を減らす判断を計画内で言及
4. ユーザーが「Slack メンテで使えない」等と言った場合は**完全 skip** する（代替経路を勝手に試さない。`x-ops` スキル側の「ユーザー承認主義」と整合）

### サブエージェント起動失敗
- 1つ失敗 → 他の結果で続行
- 複数失敗 / 全滅 → **実行モード節の「直列 inline モード」** に切替。再 dispatch を無限リトライしない

### その他
- `persona/` が空 or 欠損 → Step 2 の前にヒアリングで埋める（x-ops スキルの初期化フロー参照）
- Step 1 の素材がゼロ → 「今週は発信する素材が薄い。日々のメモ取り改善を提案」で終了
- Step 3 の下書きがすべて NG 判定 → 計画を1度だけ差し戻してリトライ。2度目の NG は人間に判断を戻す
